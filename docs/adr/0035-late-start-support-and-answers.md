# ADR 0035: 遅れて出撃する隊と応援を回答のファイルで受け取り、番号付きの質問と終了コードを分ける

- 状態: 提案中
- 日付: 2026-11-10

## 背景

要件定義書の分割案の2は、ADR 0034の最初のPull Requestの後に、運用者の指定の値（遅れて出撃する隊と応援、
前回の編成、回答のファイル）、番号付きの質問（FRM-075）、入力のエラーと別の終了コード、回答を確かめる手順
（旧Q-092。分割案の4と分担）、FRM-090の性質のテストの枠を加えることを求めている。ADR 0034の「影響」は、
時間切れの例外が`OptimizationTimeoutError`と`ShortfallUndeterminedError`の2つに分かれていることを、終了コードを
分けるときに決めるとしていた。

利用者は2026-11-10に次を決めた（要件定義書の未決事項の19回目）。

1. 分割案の2の残りを2件に分ける。このPull Requestは、遅れて出撃する隊と応援（FRM-041、FRM-042、FRM-047、
   FRM-048）、回答のファイル、番号付きの質問と終了コード、時間切れの共通の型、FRM-090の性質のテストの枠を
   持つ。前回の編成の受け取り、`output/`の置き方（DAT-008）、総力モードの前回の編成の移動先の欄（FRM-071）は
   次のPull Requestで加える
2. 終了コードは、0を出力、2を入力のエラーと解がないことの証明、3を運用者の回答が要る、4を時間切れとする。
   時間切れの2つの例外は共通の型にまとめる
3. 前回の編成は、出力するたびに`output/<実行の時刻>/`へ編成のMarkdownとJSONを書いて上書きせず、運用者が共有した
   回のJSONを`--previous`で明示する（次のPull Requestで実装する）
4. 回答はイベントのフォルダの`answers.json`に書き、`--answers`で渡す。`settings.json`とは分ける
5. 序盤以外で延長境界時刻より前の休止（FRM-090の場合4）も番号付きの質問とし、終了コード3で終える。
   その問いには、この版では回答できないと書く
6. 回答を確かめる手順の骨子を次のとおりとする。ほかの指定で変わらない誤りは入力のエラー（2）、回答なしで
   判定に使う編成を作り、対象の（隊、時間帯）が不足でない回答は使わなかったと注記する、残りを対象の（隊の番号、
   時刻）の順に1つずつ加えて成り立つものを受け入れる（書いた順によらない）、受け入れた指定で編成して不足が
   残れば質問（3）、アプリは回答を覚えず運用者が同じファイルへ足していく。下の「回答を確かめる手順」の
   細部（誤りの範囲、注記の場合分け、受け入れの基準、最適性を示せない場合）は作成者の仮定A-41とした

## 判断

### 遅れて出撃する隊と応援

- 運用者の指定`OperatorSpecification`に、受け入れた回答の遅れて出撃する隊（`LateStart`。隊、出撃開始時刻、
  応援`SupportRef`の一覧）を`late_starts`として持たせ、OptimizerとValidatorへ同じ値を渡す。応援と指定は
  書いた順によらない並びに直して持つ（FRM-090の性質(5)）
- 編成`TeamPlan`は、隊ごとの出撃開始時刻（`TeamMembership.start_minutes`）と、応援（`Support`。メンバー、
  時間帯、応援先）を持つ。出撃開始前の時間帯は所属メンバーを出撃させず、人数、休止、リーダー不在、上限を
  判定しない。応援は応援先の出撃人数、戦力、VC、上限に数え、休止は応援を含めずに判定する（FRM-011、
  FRM-042、FRM-048）
- Optimizerは、応援するメンバーをその遅れて出撃する隊に所属させ（作成者の仮定A-16）、応援先のない出撃開始前の
  参加者を遅れて出撃する隊に入れない。応援を受ける時間帯の応援先には、所属メンバーを1人以上参加させる
- Validatorは、出撃開始時刻と応援が運用者の指定と一致するか（`SPECIFICATION_MISMATCH`）と、FRM-041、FRM-042の
  条件そのもの（`LATE_START`、`SUPPORT`）を別に確かめる。指定と一致していても条件を満たさない編成を拒否する
- 序盤の長さ1時間（`OPENING_MINUTES`）と、応援を受けられる最初の隊の第5隊（`FIRST_SUPPORTED_TEAM`）は、
  利用者が決めた固定値としてドメインの定数にする（ADR 0034と同じ置き場所）

### 回答の形式

回答は`answers.json`の`answers`の一覧で、1件は問いの対象（`target`の隊と時刻）と指定そのもの（`late_start`の隊、
出撃開始時刻、応援`support`の一覧）を持つ。質問の番号は書かない。アダプター（`json_answers_repository.py`）は
形式の変換だけを行う。形式はDAT-009に定める。この版の回答は遅れて出撃させる案だけで、隊数を減らす（FRM-005）と
明示して許す（FRM-046）は分割案の3と4で加える。

### 回答を確かめる手順

アプリケーション（`BuildTeamPlan`）が次の順に確かめる（作成者の仮定A-41）。

1. ほかの指定によって変わらない誤り（ない隊、時刻、メンバー、第1〜3隊を遅らせる、応援先が第4隊以前か遅れて
   出撃する隊自身、出撃開始前でない時間帯の応援、参加していない時間帯の応援、出撃開始前に参加する時間帯の
   応援先の欠け、ほかの隊のリーダーの応援、参加時間未定のメンバーの応援、序盤にない対象への回答）は、最適化の
   前に入力のエラーにする（`domain/answers.py`の`check_answers`）。対象が序盤かは戦闘開始で決まり、遅れて出撃
   させる案は序盤の選択肢のため（FRM-041、FRM-047）。エラーの文は名前を書かず、回答の対象と、応援の時刻と
   応援先で示す。応援は書いた順によらない並びに直して持つため、書いた位置では示さない
2. 回答なしで判定に使う編成を作る。不足があり最適性を示せなければ時間切れのエラーにする（FRM-090の性質(6)）
3. 回答を、対象の隊の番号、時刻、指定の順に並べ、1つずつ確かめる。書いた順によらない（A-10の例2）
   - 対象の（隊、時間帯）がそのときの編成で不足でなければ、使わなかったと注記する。ただし、判定に使う編成で
     不足だった対象が、受け入れた指定と同じ指定で直った場合は、その対象自身への指定で直ったものとし、注記
     しない（FRM-090の性質(3)）
   - 先に受け入れた回答と同じ指定で、対象がまだ不足のままの回答は、同じ指定では直らなかったとして受け入れなかったと
     注記する。同じ隊を遅れて出撃させる別の指定（出撃開始時刻か応援が違う指定）や、同じメンバーの応援を持つ回答も、
     受け入れなかったと注記する
   - それ以外は、指定を加え、対象の休止をなくし、ほかの（隊、時間帯）に休止を新しく生まない編成をOptimizerに
     探させる（`allowed_shortfalls`。延長境界時刻より前の休止を、そのときの不足から対象を除いた組に限る）。
     ないと証明されれば、Optimizerの理由を添えて受け入れなかったと注記する。見つかった編成に不足が残り、
     最適性を示せなければ時間切れのエラーにする（FRM-090の性質(6)）。そうでなければ受け入れ、以後その編成を
     基準にする。見つかった編成が許した組の外に休止を持てば、Optimizerの誤りとして`BuildError`にする
4. 最後に受け入れた確認の編成（回答を受け入れなければ判定に使う編成）を、そのまま最後の問いと出力に使い、
   制限なしで編成し直さない。不足が残れば、番号付きの質問を示して止める。最適性を示せなければ時間切れのエラーにする。
   不足がなければ、注記とともに出力する。受け入れなかった回答の注記は、この編成で対象が不足でなければ、使わなかったと
   注記し直す（FRM-090の性質(6)「使わなかった指定の注記はその編成で判定する」）

アプリは回答を覚えない。運用者は同じファイルへ回答を足していき、毎回この手順で確かめ直す。参加者一覧や
設定を変えた場合も同じ手順で確かめ、変えたことで対象が不足でなくなった回答は注記になる（FRM-090の性質(1)の
「それらを変えた場合の扱い」）。

受け入れの判定には「見つかる」こと（存在）を使う。見つからないことはOptimizerの証明（`ProvenInfeasible`）で
だけ判断し、時間切れはそのまま時間切れのエラーにする。見つかった編成に不足が残る場合は、後の回答の判定と
問いがその編成に左右されるため、最適性を示せなければ時間切れのエラーにする（FRM-090の性質(6)「回答を確かめる
探索で最適性を示せなければ、時間切れのエラーとする」）。不足が残らない編成は、最適な編成でも不足が0のため、
最適性を示せなくても受け入れ、最後の出力はFRM-049に従う。

### 番号付きの質問と終了コード

- 延長境界時刻より前の休止は、隊と、序盤かどうかでまとめた番号付きの問い（`ShortfallQuestion`）にする。並びは
  隊の番号、最初の時刻の順とする。各問いには、まとめた（隊、時間帯）をすべて示す（FRM-090のまとめる規則）。
  序盤の問いには回答に書く対象（最初の時刻。運用者は直したい時刻を1つ書き、書いた時刻の休止がなくなる回答だけを
  受け入れ、残りの時刻は次の実行で改めて問う）と、
  受け入れられる回答がなければ参加者一覧かリーダー一覧を見直すことを示す。序盤以外の問いには、この版では回答できず
  参加者一覧かリーダー一覧を見直すよう書く
- 問いの文はアダプター（`adapters/output/shortfall_question_text.py`）で作る。CLIは問いと注記を標準エラーへ出し、
  出力を書かずに終了コード3で終える
- 時間切れの共通の型`SearchTimeoutError`をアプリケーションの境界（`application/ports.py`）に置き、
  `OptimizationTimeoutError`と`ShortfallUndeterminedError`の両方に継承させる。CLIは終了コード4で終える
- 入力のエラー、解がないことの証明（`NoValidPlanError`）、再試行の上限（`BuildError`）は従来どおり終了コード2とする

### FRM-090の性質のテストの枠

`tests/answer_world.py`に、受け入れた遅れて出撃する隊から下限の不足を決める架空の世界のOptimizerとValidatorを
置き、`tests/test_answer_properties.py`でHypothesisにより性質(1)(2)(4)(5)(6)を確かめる。分割案の3と4で選択肢を
加えるときに、この枠へ性質のテストを足す。

## 代替案

- 回答を`settings.json`のキーにする: 渡すファイルは減るが、編成の前に決める指定と問いへの答えが混ざるため
  採用しない（利用者の決定4）
- 序盤の休止だけを質問にし、序盤以外は終了コード2のままにする: この版で答えられる問いだけを質問にできるが、
  分割案の3で選択肢を加えると終了コードが変わるため採用しない（利用者の決定5）
- 時間切れも終了コード2にする: 終了コードの種類は少ないが、時間切れは再実行で直り得るため、利用者の決定2で
  分けた
- 回答をすべて加え、同時に成り立たなければ止める: 手順は単純だが、受け入れられる回答まで捨て、FRM-090の
  性質(2)の「まだ決まらない（隊、時間帯）だけについて示し直す」を満たさないため採用しない
- 受け入れを、回答を加えた最適な編成で対象が直るかで判定する: 最適化を1回減らせるが、同じ休止の数で対象の
  代わりにほかの不足が残る編成を選んだ場合に、成り立つ回答を拒否するため採用しない
- 回答を受け入れた後、最後の問いと出力のために制限なしで編成し直す: 受け入れた指定のもとで休止の数が最も少ない
  編成で問えるが、判定に使う編成になかった（隊、時間帯）に新しく休止を置く編成を選び得る。その対象は運用者が
  まだ問われていない不足で、FRM-090の「判定に使う編成と比べて新しく下限を下回る（隊、時間帯）が出ない」と、
  性質(2)の「まだ決まらない（隊、時間帯）だけについて示し直す」に反するため採用しない。制限のもとで最適な編成と、
  制限なしの最適な編成で問いの数が違う入力があるかは確かめていない

## 影響

- 終了コードの契約が変わる。以前は下限の不足と時間切れも終了コード2だった。自動化している運用者は、3（回答が要る）と
  4（時間切れ）を扱う必要がある
- 回答を受け入れるたびにOptimizerを1回追加で動かすため、回答の数に比例して時間がかかる
- 既定の探索設定（8並列、実時間の制限）は、同じ評価の編成のどれを選ぶかが実行ごとに変わる（D-012）。休止が
  隊の間で入れ替えられる入力では、問いの対象の隊が実行ごとに変わり、前の実行の問いへの回答が使わなかった注記に
  なることがある。FRM-090の性質(5)は、決定的な探索設定でだけ成り立つ。分割案の3（FRM-038、ADR 0019の見直し）で解消する
- 応援が休止の解消に効くのは、遅れて出撃する隊のメンバーが応援先の隊の唯一の参加者でない場合に限られる。序盤の
  8人（FRM-040）を分割案の4で加えると、応援の主な用途（8人に満たない隊を埋める）が使えるようになる
- FIXの隊（FRM-048、FRM-072）、グループ内に応援を限る条件（FRM-042、FRM-111）、隊数を減らした場合の指定の失効
  （A-03）は、それぞれの指定を加える分割案の5と3で扱う
- 残る事項（次のPull Request）: 前回の編成の受け取り、`output/`の置き方（DAT-008）、総力モードの前回の編成の
  移動先の欄（FRM-071）
