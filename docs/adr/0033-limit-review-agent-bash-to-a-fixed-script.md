# ADR 0033: Review AgentのBashを固定のScriptと閉じた文法に限る

- 状態: 提案中
- 日付: 2026-11-06

## 背景

ADR 0018は、読み取り専用のReview AgentにBashを残し、コマンドの文字列を許可リストで照合した。PR #10の
再レビューでは、語中の`#`、`$'...'`の展開、ブレース展開、Optionの略記と束ねた短いOptionを使うと、照合を
通ったまま書き込みや任意のコマンドの起動ができることを再現した。直すたびに同じ種類の経路が見つかった。
Shellの文法とコマンドごとのOptionを文字列から判定し続ける方式に、終わりはない。

担当の確認の手段を調べるため、利用者のClaude Codeの実行記録に2026-11-06の時点で残っていた、4つのReview
Agentの44回の実行（PR #10のレビューと、このADRの変更の最初のレビュー）のBashの呼び出しを、Tool呼び出しのIDで
重複を除いて数えた。回数はHookに拒否された呼び出しを含む。各呼び出しを、改行と`;`、`&`、`|`の直後に現れる
コマンド名で判定し、上の行から順に最初に当てはまった1区分へ入れた。

| 区分 | 回数 | うちHookの拒否 |
|---|---|---|
| `python -m pytest`か`python tools/check.py` | 10 | 4 |
| それ以外で`python`、`node`、`npx`、`chromium` | 26 | 20 |
| それ以外で`git` | 163 | 29 |
| それ以外（`grep`、`sed`、`ls`など） | 462 | 40 |
| 合計 | 661 | 93 |

検索と履歴の確認が大半で、テストの実行は多くない。ただし、担当が自分で裏取りできる手段は残す価値がある。
対象はハーネスの変更のPull Requestだけで、編成ルールの変更では割合が変わり得る（作成者の仮定）。

## 判断

ADR 0018のうち、許可リストの判断（「許可リストに一致するBashコマンドだけを通し」の部分、「Bashで許可するのは」
と`pytest`を許可する理由の項、影響の「許可リストにない確認コマンド」の項）を置き換える。ADR 0018の影響の
「Hookの追加と変更は、Claude Codeの新しいSessionから有効になる」は、登録の変更に限る。読み取り専用をHookで
強制することと、matcherの範囲は変えない。

- Review AgentのBashは、固定のScript`python tools/review_query.py`の呼び出しだけを、閉じた文法で通す（利用者の
  判断、2026-11-06）
- Hookはコマンドの意味を解釈せず、文法に完全一致するかだけを見る。引数は空白1つで区切り、「英数字と
  `_./:=@,+%~^-`だけの語」か「単一引用符で囲んだ文字列（`'`と改行を含まない）」に限る。語頭の`~`と、`=`か`:`の
  直後の`~`は展開されるため拒否する。bashは`a=~/x`の形の引数でも`~`を展開する（2026-11-06のレビューで
  再現）。この形ではShellの展開も区切りも起きない（文字の定義は作成者の判断）
- GitとpytestのOptionの意味は`tools/review_query.py`へ閉じ込める。操作は`status`、`list`、`grep`、`diff`、`log`、
  `commit`、`show`、`test`とし、担当が渡せるのはパス、リビジョン、検索語、`tests/`の下のpytestのテストの指定、件数だけと
  する。Optionとして読まれる値、Repositoryの外を指すパス、Gitのpathspecの魔法は受け付けない（作成者の判断）
- Gitが対象にしないパスを`grep`と`list`へ渡すとエラーにする。除外されたファイルや打ち間違いが「一致なし」に
  見えると、確認を誤るためである。`tmp/`などGit管理外のファイルはReadで読む（作成者の判断）
- Agent定義の`tools`は変えない。確認が足りないときは、Hookの文法ではなくScriptの操作を足す（作成者の判断）
- `agent_type`がないか`null`なら主Sessionとして通し、それ以外の文字列でない値は拒否する（作成者の仮定）
- 編成または表示の変更では、主エージェントが`sample/`の`tools/preview_output.py`の出力を作って担当へ渡す。
  担当はこのScriptを実行できない（作成者の判断）
- Git保護の照合は残す（利用者の判断、2026-11-05）。`git reset --hard`や`git clean`は手元の操作で、サーバー側では
  止められない
- Git保護は2つの判定を行い、厳しいほうを採る。1つ目は変更前と同じ判定で、引用符を解釈せずにすべての区切りで
  分け、字句解析に失敗した区間は読み飛ばす。これにより、変更前に拒否または確認していた入力は、構造上必ず
  同じかより厳しい判定になる。1つ目を先に行い、2つ目の判定に左右されずに拒否を返す。2つ目は引用符を解釈する
  判定で、変更前が見逃していた入力を加えて止める。括弧の対応、パイプの検索、区間の最初の語の判定、`-c`の
  走査は、同じ部分を読み直さないようにする。直すたびに、時間が入力の長さの2乗で増える別の経路が見つかった
  （4回。閉じない`$(`、ヒアドキュメントの記号、`|`と`(`の並び、`bash -o`の並び。いずれも直した。
  2026-11-08のレビューと計測）。時間切れのHookは判定を出さず、通常のpushの確認が出なくなる。未知の経路に
  備え、2つ目の判定は2万文字以下の入力にだけ行い、超えた入力は1つ目の判定だけにする（利用者の判断、
  2026-11-08）。2万文字は、日常のコミットのコマンドより十分長く、未知の経路が2乗で増えても数秒で終わる長さとした。
  入れ子の`eval $(…)`の8段（各段に行継続を含む）でも、2万文字で0.81秒だった（作成者の判断と計測）。上限を
  超えた入力を拒否か確認へ回す案は採らなかった。長いヒアドキュメントを含む日常のコマンドを止め、変更前より
  厳しくなるためである（作成者の判断）。
  引用符の解釈を細かくするたびに、Shellと解釈がずれて変更前に止めていた操作を通す経路が見つかった
  （`'\''`、改行をまたぐ引用符、コメントやヒアドキュメントの本文の`'`、`bash --login -c`、`pwsh -Command`、
  PowerShellの`\"`など。2026-11-06と2026-11-08のレビューで再現）。2つ目の判定だけに頼らないのはこのためである
  （作成者の判断）
- 2つ目の判定では、閉じた引用符の中の`;`、`|`、`&`、改行は区切りとして扱わない。引用符の範囲は左から走査して
  決め、`\`の退避と改行をまたぐ引用符を扱い、語頭の`#`から行末まではコメントとして引用符を数えない。最後まで
  引用符が閉じないときは範囲を信用せず、すべての区切りで分ける。`$(...)`、バッククォート、`sh`や`bash`などの
  `-c`の文字列、`eval`の引数はShellが実行するため、引用符の中でも中身を別のコマンドとして区切って判定する。
  `-c`の文字列は、bashと同じく、Option（`-c`の後のものを含む）と`--`か`-`の後にある最初の語とする。`o`か`O`を
  含む短いOptionのまとまり（`-euo pipefail`）と`--rcfile`、`--init-file`は値を読み飛ばす。単一引用符、コメント、
  区切りを引用符で囲むか`\`を付けたヒアドキュメント（`<<'EOF'`、`<<"EOF"`、`<<\EOF`）の本文の`$(...)`とバッククォートは実行されないため判定
  しない。Claude Codeの既定のコミットの形`git commit -m "$(cat <<'EOF' … EOF)"`の本文に`` `git push` ``と書いても
  止めないためである（2026-11-08のレビューで再現）。入れ子は8段まで判定し、それより深い分は2つ目の判定では
  読まない（1つ目の判定は行う）。`$(...)`の範囲は、単一引用符、二重引用符、コメント、引用符付きのヒアドキュメントの本文の括弧を数えずに決め、
  `$(`の中では引用符の状態を新しく始め、閉じたら外側の状態へ戻す。`\`で退避した括弧も数えない。コミットの本文の`1)`で範囲を誤り、本文のバッククォートを判定していた
  （2026-11-08のレビューで指摘）。引用符付きの本文はデータとして区切りの判定から除き、区間の最初の語が
  Shellのとき（`bash <<'EOF'`、`(bash <<'EOF'`）と、記号と同じ行にShellへのパイプがあるとき（`cat <<'EOF' | sh`）
  だけ、本文をコマンドとして判定する。`sudo bash`や`env bash`のように別の語を挟む形は判定しない（変更前も
  止めない。作成者の判断）。単独の`&`も区切りとして扱う。字句解析できない区間は読み飛ばさず、
  語に分けて同じ判定にかける。行末の`\`は行継続と見分けられないため、連結の前と後の両方を判定する。通常のpushが先にあっても、
  後ろの区間の拒否を優先する。これは事故を防ぐための照合であり、変数やエイリアスを使って意図的に回避する操作は
  止められない（作成者の判断）

## 代替案

### Review AgentからBashを外す

利用者は2026-11-05にこの案を選んだが、作成者が実装してレビューを受けた後、2026-11-06に利用者が取りやめた。
Bashがないとテストと履歴の確認は主エージェントへ依頼することになる。依頼は主Sessionの権限で動き、
`pytest --basetemp`のように見た目はテストで書き込む依頼を語の説明では止められないため、照合で解けなかった問題が
主エージェントへ移る。

作成者が2026-11-06に利用者へ示した判断の材料には誤りがあった。「Agent定義に`Grep`と`Glob`を書いても担当には
渡らない」と説明したが、担当には渡る場合があった。実行記録の観察は次のとおりである。

| Claude Code | 定義の`tools` | 実行 | 観察 |
|---|---|---|---|
| 2.1.317 | Bashあり | 44回 | Grepを呼んだ1回の実行は、3回の呼び出しがすべて「No such tool」。ほかの43回はGrepもGlobも呼んでいない |
| 2.1.318 | Bashなし | 4回 | GrepとGlobが動いた |
| 2.1.318 | Bashあり | 1回 | GrepもGlobも「No such tool」。担当の定義にはRead、Bashだけが見えた（2026-11-06の実機確認） |

同じ版でBashの有無により結果が分かれたため、原因は版ではなくBashの有無と見る（1回の実行からの推定）。Bashを
残す以上、担当の検索は`review_query.py`が担う。利用者は訂正を受けて、次の理由でこの案を採らなかった
（2026-11-06）。固定のScriptなら検索が版の挙動に左右されず、担当が自分で裏取りできる。代償として、Scriptと
そのテストを保守する。

### 許可リストの照合を強める

引用符の外の`$`と`{`の拒否、略記の照合、`sort`の除外で、見つかった経路は塞げる。しかし、同じ種類の経路が
残り、コマンドごとの知識を保守し続けることになる。

### OSのsandboxを使う

ADR 0018の理由に加え、Dev Containerには`bwrap`がなく、`unshare`も拒否された（2026-11-05に確認）。Containerの
制限を緩めない判断（ADR 0032）を覆すことになる。

### 字句解析できないGitの区間を一律に拒否する

最も単純である。しかし、本文の`'`で字句解析に失敗することは珍しくない。PR #10の作業Sessionの主エージェントの
Bash 70回を、`COMMAND_SEPARATOR`で分けた区間ごとに`shlex`で確かめた（2026-11-06）。39回に失敗する区間があり、
そのうち17回は失敗した区間に単語としての`git`を含んでいた。`git`を含む区間に限っても日常のコマンドが止まるため、
採らなかった（作成者の判断）。

## 影響

- Scriptとそのテストを保守する。Gitの版を上げるときは、Scriptが渡すOptionの動作も確かめる
- 2万文字を超える入力では、2つ目の判定だけが止める形をGit保護が見逃す。`$(...)`とバッククォートの中、
  引用符で囲んだ`sh -c`と`eval`の文字列、Subshellの`(git …)`、字句解析できない区間（`# don't`のようなコメントを
  含む行）である。ヒアドキュメントの本文の行と引用符のない`eval`の引数は、1つ目の判定が行ごとに止める。
  どれも変更前と同じ扱いである（利用者の判断、2026-11-08。2万1文字の入力で主エージェントが確かめた）
- 担当は`python tools/check.py`を実行できなくなった。これに含まれる`tools/sync_agent_config.py`の照合、
  Ruff、mypy、`tests/web/`のJavaScriptのテストも同じである。`$review-kvk-change`では主エージェントが委譲の
  前に1回実行し、結果を担当へ渡す
- `tools/preview_output.py`は、自身と同じ作業ツリーの`src`を先に読む。editable installは元の作業ツリーの
  `src`を指すため、Session用worktreeで作った出力が変更前のコードで編成されていた
- 担当の`pytest`はこれまでどおりGit管理外のCacheと一時Directoryへ書く。テストのコードは実行される
- `.env.*`を`.gitignore`へ足す。`git grep --untracked`が読むのは除外されていないファイルで、`permissions.deny`は
  このScriptに効かないためである
- Codexには適用されない。Codexでは、従来どおり`sandbox_mode`と指示文で読み取り専用を守る。Git保護の変更は、
  `$git-guardrails-codex`で導入済みの環境へ再度コピーするまで届かない
- `.claude/settings.json`の登録の変更は新しいSessionから、登録済みのScriptの本体の変更は次の呼び出しから効く。
  `.claude/agents/`の`tools`と本文は実行中のSessionの担当へ届かず、Sessionの開始時の版で動く（2026-11-06の担当の
  実行での観察）
- Scriptは文字の扱いに次の制限がある。`test`のノードIDは空白とASCII以外を受け付けず、該当する`parametrize`の
  ケースは関数単位で実行する。検索語の中に`'`は書けないため`.`で代用する。Git Bashのパス変換が`/`で始まる検索語を
  変える疑いがある（未確認）
- Git保護は、`'`を含むヒアドキュメントの本文の行にも反応する。テストの文字列を書くヒアドキュメントが、
  `git branch -D`の語で拒否された（2026-11-06）。変更前と同じ判定は、引用符の範囲を解釈しないためである。
  この場合はBashを通さず、編集のToolで書く
- 実機の確認の結果（2026-11-06、Claude Code 2.1.318、`kvk-test-reviewer`の1回の実行）。`.claude/agents/`の
  `tools`にGrepとGlobを書いていても、担当に渡ったのはRead、Bashと報告用のToolで、GrepとGlobの呼び出しは
  「No such tool」になった。`python tools/review_query.py`の`status`、`grep`、`test`は通り、`git status`、
  `cat README.md`、`python tools/review_query.py status; cat README.md`はHookが拒否した
- 「No such tool」の文はBashの`grep`と`find`を案内するが、担当のBashでは使えない。担当への指示は
  `review_query.py`の`grep`と`list`を案内する
