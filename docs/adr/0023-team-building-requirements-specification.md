# ADR 0023: KvKチーム編成の要件定義書を目標仕様の正本とする

- 状態: 提案中
- 日付: 2026-10-18
- 改訂: AGENTSの「正本と優先順位」に、要件定義書と現行の動作の関係を追記した
- 注記: パッケージ名は、ADR 0026で改名した後の名前に書き換えた。当時の表記は旧Repositoryの履歴にある

## 背景

現行の編成ルール（README、AGENTSの「現行のプロダクトルール」、`team_master.json`）は、A〜Kの11隊固定、
時間帯ごとのチーム移動あり、A〜Cは8人・VC必須・戦力`A > B >= C`というモデルである。一方、実際の運用は、
利用者がRepositoryの外で管理する2つのルール文書（同盟メンバー表の整形ルール、チーム編成ロジック v2と
2026-10-10の確定分）に従っており、所属固定、リーダー数で決まる隊の数、★やT11の配置、総力モードなど、
モデルの前提から異なる。ルールの正本がRepositoryの外にあるため、実装との差や変更の根拠を追えない。

利用者は2026-10-18に、2つのルール文書をプロダクトの編成ルールの正本とし、所属固定のモデルへ置き換える
こと、戦闘時間を設定値とすること、アプリの最終出力をチャット共有用テキストだけとし、時間帯別の情報は
画面で確認・操作することを決めた。

## 判断

- `docs/requirements/team-building/`の要件定義書を、編成ルールの**目標仕様の正本**とする
- 要件に、必須条件、警告、目的関数、入力正規化、運用操作、表示のみ、非機能、廃止の分類とIDを付ける
- README、AGENTSの「現行のプロダクトルール」、architecture、domain-modelは、実装が置き換わるまで
  **現行の動作**を説明する。実装Issueが完了するたびに、該当する要件で現行の記述を置き換える
- 文書内の食い違いと運用上の判断が必要な点は未決事項に分け、決めてから実装する
- 運用値（戦闘時間、リーダー、人数の上限、呼び名の対応、グループ分け）は要件定義書に値を書かず、
  設定として持つ。実運用の参加者名は要件定義書とテストへ含めない
- Excelは出力しない。依存（openpyxlなど）も追加しない

## 代替案

### 現行のモデルを維持し、運用ルールとの差を運用で吸収する

実装の変更は不要だが、所属固定や★の配置など運用の中心的な規則をプロダクトが扱えず、利用者が手作業で
調整し続けることになるため採用しない。

### 要件定義書を作らず、ルール文書から直接実装する

早く着手できるが、文書内の食い違い（稼働7人の許容範囲など）を実装者が推測で決めることになり、
変更の根拠も残らないため採用しない。

### 現行のREADMEとAGENTSを、要件定義書の内容へすぐ書き換える

正本は1つになるが、実装と利用者向けの説明が食い違い、現在のCLIの動作を誤って案内するため採用しない。

## 影響

編成ルールの正本が、目標仕様（要件定義書）と現行の動作（README、AGENTS）の2つに一時的に分かれる。
混乱を避けるため、AGENTSの「現行のプロダクトルール」に要件定義書への導線を置き、実装Issueの完了ごとに
差分（要件定義書の「現行の実装との差分」）を減らす。実装の順序と分割は要件定義書の5章に従い、
`$change-kvk-rules`で進める。ADR 0003とADR 0021の構成（`kvk_team.team_building`）は変えない。
