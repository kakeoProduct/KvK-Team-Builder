# ADR 0025: Hypothesisで必須条件の性質テストを決定的に行う

- 状態: 提案中
- 日付: 2026-10-19

## 背景

必須条件（時間帯ごとの重複・未配置なし、人数上限、A〜Cが8人かつ全員VC可能、固定集結主と
代理、`A > B >= C`）は、手で作った少数の例で検証していた。人数ちょうど、同じ戦力、途中参加、
代理集結主など境界の組み合わせを網羅できず、Validatorが不正な候補を見逃す退行に気づきにくい
（#45）。

性質テストのライブラリHypothesisは、性質を書くと入力を生成し、失敗時は最小の入力へ縮めて
報告する。一方で既定の設定は、このRepositoryの方針と次の点で合わない。

- 入力の固定（`derandomize`）が既定で有効になるのはCI上だけで、手元では無作為な入力になる。
  `AGENTS.md`は無作為なテストデータを禁じている
- 1件あたり200msの制限時間（`deadline`）が既定で有効で、CP-SATは1回の解決で超えやすい。
  ADR 0019で解消した、実行環境の速さに依存する失敗が戻る
- 失敗例を`.hypothesis/`へ保存し、次回はそれを優先して再実行するため、手元だけ結果が変わる

## 判断

- 開発依存に`hypothesis>=6.170,<7`を加える。実行時依存は増やさない
- `tests/conftest.py`でProfileを登録して読み込み、`derandomize=True`、`database=None`、
  `deadline=None`、`print_blob=True`をテスト全体へ適用する。CIかどうかの自動判定に依存しない。
  HypothesisはCI上で`ci` Profileを自動で読み込むため、Profileの親には組み込みの`default`
  Profileを指定し、`ci` Profileの値を引き継がない。`tests/test_hypothesis_profile.py`は
  値に加えてProfile名を検査し、CI上でも`tests/conftest.py`の読み込み漏れを検出する。
  同じファイルの構造テストが、`tests/`でテストごとに`derandomize`、`database`、`deadline`を
  上書きする`@settings`と、`@seed`、`@reproduce_failure`を検出する
- 生成戦略は`tests/team_plan_strategies.py`に置き、必須条件を満たす参加者と配置を構成的に作る。
  D〜Kの8人未満、集結主の到着待ち、時間帯の境界とずれた参加時刻、待機参加者を含める。
  途中参加と途中離脱はD〜Kだけに生成し、A〜Cは全員が全時間帯に参加する。A〜Cの集結主の
  到着待ちや、時間帯ごとのA〜Cの入れ替えは、8人固定と戦力関係を時間帯ごとに保つ生成が
  大きくなるため、この判断の対象外とする
- Validatorの性質テストは、有効な編成に必須条件を1つだけ破る変更を加え、期待するコード、
  チーム、時間帯だけを必須条件エラーとして返すことを検証する。見逃しと誤検出の両方を
  検出するためである。有効な編成では、8人未満と到着待ちの警告が該当するチームと時間帯の
  すべてに出ることも検証する
- Optimizerの性質テストは、有効な編成が存在する参加者を生成し、`deterministic_rules()`で
  最適化した結果を独立Validatorが受理し、開始時刻の未定な参加者が待機枠にあることを検証する。
  1件で数秒かかるため5件に絞る

## 代替案

### 手書きの例を増やす

意図は読みやすいが、境界の組み合わせを網羅できず、例が増えるほど保守量も増える。既存の例は
残し、性質テストを補完として加える。

### Hypothesisの既定設定を使う

手元では無作為な入力になり、制限時間と失敗例の保存によって実行環境に依存する失敗が起きる
ため採用しない。

### テストごとに`@settings`で決定性を指定する

指定漏れのテストだけ無作為になり、レビューで見落としやすい。Profileで一括して適用し、
テストでは生成件数だけを必要に応じて変える。

### Validatorと同じ判定をテスト側にも実装し、無作為な編成の判定結果を比べる

Validatorの判定を写すだけになり、同じ誤りを両方へ入れやすい。変更の種類から期待するコードが
決まる構成的な生成を採用する。

## 影響

- Validatorの性質テストは12件で約30秒、Optimizerの性質テストは約8秒かかる
- 生成戦略は既定のJSONチームマスタの形（VC必須のA〜Cが同じ人数で固定、D〜Kに不足を警告に
  する人数幅がある、戦力関係が`A > B >= C`）を前提にする。人数の上限はチームマスタから読む。
  前提は`master_assumption_errors()`にまとめ、崩れた場合は
  `test_strategies_match_team_master`が理由を示して失敗する。その場合は戦略を見直す
- Hypothesisは更新が頻繁で、版が変わると固定した入力の並びも変わる。更新後に新しく失敗した
  場合は、新しく見つかった反例として原因を調べる。版の上限を上げるときは品質ゲートの
  実行時間も確認する
- Hypothesisは、読み込み済みの手元のモジュールから定数を集めて生成に使い、その抽出結果を
  `.hypothesis/constants/`へキャッシュする。`database=None`でも作られるが、ソースのハッシュを
  キーにしたキャッシュのため結果を変えない。`.hypothesis/`はGit管理外とする。ただし定数の
  候補は読み込み済みのモジュールで変わるため、テストを一部だけ実行したときと、
  `python tools/check.py`で全体を実行したときで、生成される入力が異なる場合がある。合否は
  全体を実行した結果で判断する
- 失敗時は縮小された入力と`@reproduce_failure`の再現用コードが表示される。再現用コードは
  調査中だけ使い、コミットしない
