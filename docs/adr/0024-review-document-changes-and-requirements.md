# ADR 0024: 文書だけの変更もレビューし、要件レビュー担当を加える

- 状態: 提案中（一部をADR 0026で置き換え）
- 日付: 2026-10-18
- 置き換え: ADR 0002とADR 0007のうち、レビュー担当をドメイン、アーキテクチャ、テストの3観点とし、
  主エージェントのフォールバックも同じ3観点とする点。ADR 0022のうち、読み取り専用の例外を
  `tmp/reviews/`への保存と投稿だけとする点と、指摘への対応後は対応状況を更新して投稿し直すとする点
  （再レビューへ置き換える）

## 背景

`$review-kvk-change`はドメイン、アーキテクチャ、テストの3観点のレビュー担当で構成され（ADR 0002、
ADR 0007）、文書だけの変更では「コードを変えていない」ことを理由にレビューを省略してきた。一方、
要件定義書（ADR 0020など）は実装の根拠になる正本であり、出典との食い違い、考慮漏れ、曖昧な
表現があると、後続の実装がそのまま誤る。既存の3観点は実装とテストの退行を見るもので、要件が出典を
正しく写しているか、実装者の解釈が割れないかを確かめる担当がいない。

利用者は2026-10-18に、文書だけの変更でもAIレビューを行い、要件が正確か、考慮漏れがないかなど、
要件定義の不足を観点として持たせることを求めた。

## 判断

- 差分があれば、コードだけの変更でも文書だけの変更でも`$review-kvk-change`を行い、省略しない。
  理由を書けば見送れるのは、意味を変えない誤字の修正だけの変更、共有記憶（`docs/project-memory/`）だけの変更、意味を変えない誤字の修正とそのセッションの共有記憶の記録だけを含む変更の3つに限る。
  要件ID、数値、否定、識別子、規則の対象を変える修正は、誤字の修正に含めない（利用者が
  2026-10-18に承認）。3つ目は、変更のあるセッションは共有記憶を記録するため、誤字の例外が使えなくなるのを防ぐ（利用者が
  2026-10-18に承認）。`$implement`の仕上げと`$create-github-pr`の作成前の両方で、この規則に従う
- 4つ目の読み取り専用のレビュー担当`kvk-requirements-reviewer`を加える。観点は、出典との一致、
  考慮漏れ、曖昧さ、矛盾、検証可能性、要件IDの整合、秘密情報の混入とする
- 4つの担当は、変更の種類にかかわらず常に全員を割り当てる。要件レビュー担当は、コードだけの変更では
  実装が要件定義書、`team_master.json`の運用値、出典に合っているかを確かめる
- 名前付きエージェントを使えない環境では、主エージェントが4つの観点（要件の観点を含む）を順に確認する
- Repositoryにない出典（利用者のルール文書、会話で受け取った資料）は、受け取った時点でGit管理外の
  `tmp/review-sources/`に保存し、その絶対パスをレビュー担当へ渡す。実運用の名前を含むためコミット
  しない。読み取り専用の例外に、`tmp/review-sources/`への保存を加える
- 出典にある実運用の参加者名は、レビュー結果（`tmp/reviews/`）とPull Requestのコメントへ転記せず、
  役割や匿名の表記で書く。投稿したコメントは編集も削除もしない（ADR 0022）ため、転記を防ぐ
- 秘密情報として扱うのは、参加者一覧や出典に由来する情報（参加者名、戦力値、VC可否、参加時刻）と
  TOKENなどである。READMEと`team_master.json`に契約として載る集結主名、人数、イベント時間は対象外。
  基準ブランチにコミット済みの`tests/`と`sample/`の試験データにある名前は、レビュー結果へ書いてよい。
  レビュー対象の差分で新しく加わるデータが出典に由来しないかは、引き続き検査する（利用者が2026-10-18に
  承認）
- 指摘へ対応した後は、対応後の差分をもう一度レビューする（再レビュー）。対応状況の更新だけでは、
  対応が指摘を正しく解消したか、対応によって新たな問題が生じていないかを確かめられないため。
  再レビューは前回の指摘ごとの判定と新たな問題を確かめ、今回の結果に`Must`がなく前回の`Must`が
  すべて「解消」で、残った`Should`がすべて修正済みか利用者が見送りを選び、運用者への確認事項が
  すべて回答されて正本へ反映されるまで繰り返す。別のPull Requestへ引き継いだ確認事項と「保留」の回答は
  回答済みとする。確認事項が未回答の場合と、前回の`Must`に「解消」以外がある場合の承認判定は
  「承認不可」とし、ADR 0007の承認判定を補う（利用者が2026-10-19に承認）。`Must`はリスクを受け入れても見送れない
  （利用者が2026-10-18に承認）。結果は新しいコメントとして投稿する。対象はPull Request全体の
  差分とし、前回のレビュー以降のコミットを重点に見る（利用者が2026-10-18に承認）。amendやrebaseで
  対応しても対象が割れないようにするため。投稿の前に、対象のheadがpush済みで、同じheadの結果が
  まだ投稿されていないことを、`target`、`head`、`diff`の組で確かめる。確かめられない場合は投稿もpushもしない。利用者が`Should`の
  見送りを選んだ場合は、レビュー結果の「見送り」の節に記録し、受容したリスクをPull Request本文の
  「判断と影響」へ書く（利用者が2026-10-18に承認）。本文への追記は`$review-kvk-change`が利用者の
  承認を得て行い、読み取り専用の例外に加える。作成者の仮定を本文へ載せるときも、同じ方法で利用者の承認を得る。Pull Requestがまだない場合は、`$create-github-pr`が
  作成時に写す。同じheadへ結果を投稿し直さずに、承認する人間が受容の経緯をたどれるようにするため。
  見送りの記録は再レビューで引き継ぎ、対象の箇所がその後のコミットで変わったら改めて判断する（利用者が
  2026-10-19に承認）
- `$implement`はコミットする前の変更をレビューする。このため、レビューの基準のコミットからの変更の
  指紋を`tools/review_fingerprint.py`で記録し、コミット後の範囲から計算した指紋と一致すれば、同じ版を
  レビューしたとみなして投稿する（利用者が2026-10-19に承認）。Readyにしてよいこと、委譲の前に計算すること、
  変更がなくても記録することは、レビューの指摘への対応である。共有記憶はレビューの後に
  記録するため、指紋から除く。PRを作った後に4担当でもう一度レビューする案は、費用が2倍になるため、
  先にコミットしてからレビューする案は、`$implement`の手順を大きく変えるため採らない。指紋は名前の
  変更を検出せずに計算し、未追跡のファイルを含める。PRがある状態でまだpushしていない結果は、
  `$implement`がpushした直後に投稿する（利用者が2026-10-19に承認）。名前の変更を検出しないこと、
  未追跡のファイルを含めること、重複を`target`、`head`、`diff`の組で判定することは、レビューの指摘への
  対応である。pushの前に再レビューを重ねた場合に最後の結果だけを投稿するのは、作成者の判断である
- 指摘へ対応するたびに自己改善する。作成者は再レビューの前に自己点検リスト
  （`.agents/skills/review-kvk-change/references/self-check.md`）を確かめ、再レビューの後に指摘の原因を
  分類して「振り返り」に書く。リストにない原因が同じPull Requestで2回以上現れたら、レビューは項目の
  案を書き、作成者が次の対応の最初にリストへ反映する。レビューは読み取り専用のままとする。共有記憶の
  昇格には利用者の承認が要る（AGENTS）が、自己点検リストへの項目の追加と書き方の見直しを次の対応で
  反映することは、項目ごとの承認を要らないこととする（利用者が2026-10-19に承認）。反映はPull Request
  の差分として再レビューを受ける。手順そのものを変える場合は利用者へ提案する。回数は、分類が現れた
  再レビューの回数で数える。繰り返しを終えた後に残った案を共有記憶の昇格候補へ写さず、投稿した
  レビュー結果に残すのは、昇格候補の作成条件（独立した複数のセッション）と食い違わないようにするための
  作成者の判断である
- 運用者への確認事項は、必須条件の判定、出力の可否、運用者の操作のどれかが変わる点だけに絞り、
  推奨案を添える。ただし、出典や回答どうしの衝突は、影響の範囲にかかわらず確認事項にする（AGENTS）。
  それ以外の細部は作成者が既定案を決め、作成者の仮定として記録する。再レビューのたびに細部の質問が
  増え、運用者の負担が大きくなったため（利用者が2026-10-19に依頼）。記録先は変更の種類ごとに
  `$review-kvk-change`の表に従い、ADRの「判断」とPull Request本文だけに書くのは、ハーネスの変更でADRを作るか更新する場合に限る。
  Review Agentの定義は基準を写さず、Skillを参照する。写しが正本とずれたため
- 要件の解釈で運用者の判断が必要な点は、指摘と分けて「運用者への確認事項」としてレビュー結果に
  載せる。回答が出るまで正本を推測で変更しない
- 対象のPull Requestがmergeまたはcloseされたら、`tmp/review-sources/`の資料を削除するか残すかを
  利用者に確認する

## 代替案

### 既存の`kvk-domain-reviewer`に要件の観点を加える

担当の数は増えないが、編成ルールの運用出力の退行と、要件の出典との照合という性質の違う作業が
1つの担当に集まり、どちらも浅くなる。web補助ツールの要件（`battle_timing`）も対象になるため、
独立した担当にする。

### 要件レビュー担当を、要件や文書の変更のときだけ割り当てる

費用は小さくなるが、割り当て条件の判定（どのパスを要件とみなすか、要件IDを根拠にした実装か）が
漏れやすく、`team_master.json`の運用値だけを変える変更などで出典との照合が抜ける。条件を管理する
手間も増えるため、常に全員を割り当てる。

### 文書だけの変更では、主エージェントが簡易に確認する

費用は小さいが、要件を書いた主エージェント自身が確認することになり、書いた側の解釈の偏りを
見つけにくいため採用しない。

## 影響

文書だけの変更や小さなコードの変更でも、4つの担当のレビューの費用と時間がかかる。要件の出典を
`tmp/review-sources/`へ保存する手間が増える。新しいレビュー担当の定義はClaude Codeの新しいSession
から使える。それまでのSessionでは、主エージェントが要件の観点を確認する。Codexで実行中のSessionに
新しい定義が反映される時期は確認していない。
