# ADR 0029: 総力モードの同盟移動と、個人名を含むデータの保持

- 状態: 提案中
- 日付: 2026-10-21
- 置き換え: 要件定義書のうち、FRM-084（総力モードの隊番号の振り直し）と、次の決定済みの事項の該当部分
  - 旧Q-064（ビビアン持ちを★と書く）と、旧Q-052のうち◆の表記と総力モードの隊の名簿の形
  - 旧Q-074のうち総力モードの隊の見出しの形
  - 旧Q-011（協力者を総力の合計にだけ使う点）
  - 旧Q-026、旧Q-036、旧Q-044（グループの人数と総力に、待機と参加時間未定を含めない点）
  - 旧Q-085（総力モードでは振り直した後の番号で隊を減らす点）

## 背景

2026-10-19〜21に、実運用のイベントで総力モードの編成を試算した。参加者一覧の手入力に加え、
外部の集計サイトから総力とMystic Trialを取得し、2つの同盟へメンバーを移すグループ分けを行った。
試算の中で、要件定義書（ADR 0023）が想定していなかった運用が次々に現れた。

- 移動先の同盟ごとのグループ、同盟の移動先を分けない条件、移動後の同盟の人数の上限と総力の目標
- 通常の書き方で届いた1同盟を、全員協力者として扱う運用
- リーダーの順を運用者が決め、総力で振り直さない運用
- 総力モード専用の、隊ごとの一覧と同盟移動の一覧の出力

あわせて、運用者は次の2点を求めた。
- 外部の集計サイトはなくなる可能性があるため、スクリーンショットからの入力も考えること
- 個人名を含むデータは、個人情報保護のためバージョン管理の対象外で保持し、Repositoryには保持する形式だけを共有すること

## 判断

- 試算で決めた運用を、要件定義書の目標仕様として記録する（旧Q-093〜旧Q-107）。要件レビューの
  確認事項への回答（旧Q-111〜旧Q-117、旧Q-119、旧Q-120）と、未確定の懸念への回答（旧Q-121〜旧Q-129。旧Q-123では、Git管理外の名前の対応表で今のIDと一致させる）もあわせて反映する。反映先は次のとおり
  - 同盟移動の規則: formation-rules.mdの11章（FRM-100〜FRM-106）
  - 出力: OUT-015〜OUT-018
  - 協力者同盟: ROS-007。どの同盟を指定するかは設定値とし、本書に書かない
- 取得元: 総力、Mystic Trial、同盟の名簿の取得元を、外部の集計サイト、スクリーンショット、運用者の入力の3つとし、
  どれでも同じ形式のデータを作れるようにする（ROS-051、ROS-053、DAT-003）。外部の集計サイトは任意の
  機能とし、編成の実行に必須としない
- 外部の集計サイトからの取得:
  - 取得はインフラストラクチャのアダプターが行い、DATの形式のファイルか不変なドメインの値へ変換する。
    ドメインは、取得元にもファイル形式にも依存しない
  - 認証情報はRepositoryにも`tmp/events/`にも置かず、利用者のホームの設定フォルダなどRepositoryの外に置く
  - テストとCIはネットワークを使わない
  - 取得に失敗した場合、または一部だけ取得できた場合は、理由を示して止める。古いデータと黙って混ぜず、
    ほかの取得元へ自動で切り替えない。運用者がROS-051の方法を選ぶ
  - アダプターは、取得を指示した範囲（同盟、または総力の順位表の上位N人）をすべて取得できたときだけDATの形式のファイルを書く（一部だけの取得の定義はDAT-006）。行がないメンバーは未取得として
    扱うため、途中で切れたファイルが正常な未取得のデータとして読まれないようにする。複数のファイルの置き換えが
    途中で失敗しても、新しいファイルと古いファイルを混ぜて使わない。取得の単位の外の行（DAT-006。`power_snapshot.csv`では運用者の入力やスクリーンショットの行を含む）は
    書き換えずに残し、書くときに行をまとめない。置き換えの方法は実装Issueの7のADRで決める（DAT-006）。未取得の人数は
    OUT-018（グループのない総力モードではOUT-015）に添える
- 個人名を含むデータの保持:
  - 対象は参加者一覧、名前の対応表、取得した総力、同盟の名簿、運用者の指定、編成結果とする
  - メインの作業ツリーの`tmp/events/`の下（バージョン管理の対象外）か、運用者が指定するRepositoryの外のフォルダに置く
  - Repositoryには形式と架空の例だけを、data-formats.md（DAT-001〜DAT-008）に置く
  - 個人名を含まない設定値の置き場所は、これまでどおり実装Issueの1と2で決める
- 未決事項として残す点:
  - 総力モードの同盟メンバー表（Q-108）、通常モードの隊の表示（Q-109）、最低ラインと総力の目標の使い分け（Q-110）

## 代替案

- **今回の運用を記録せず、イベントごとに作業用Scriptで対応する**: 運用者の判断が記録に残らず、
  実装Issue（分割案の7）で同じ判断をやり直すことになるため採用しない
- **外部の集計サイトを唯一の取得元とする**: サイトが止まると総力モードが使えなくなるため採用しない
- **個人名を含むデータを暗号化してRepositoryに置く**: 鍵の管理が増え、誤って平文をコミットする
  危険が残るため採用しない
- **協力者同盟の名前を要件定義書に書く**: 実運用の同盟名を本書に含めない規則（要件定義書の1章）に
  反するため、設定値とする

## 影響

- 実装Issueの7（総力モード）の範囲が広がる。アダプターの境界は「判断」のとおりとする
- 個人名を含むデータはバージョン管理の対象外にあるため、イベントの記録はローカルにしか残らない。
  バックアップは運用者が行う
- Session用のworktreeを削除すると、その`tmp/`にある管理対象外のファイルも消える。
  このため、データはメインの作業ツリーかRepositoryの外に置く（DAT-001）
- 基準ブランチにコミット済みだった実運用の名前（旧Q-118）は、ADR 0026で架空の名前へ置き換えた。
  今回の判断は、これから作る個人名を含むデータを対象とする
