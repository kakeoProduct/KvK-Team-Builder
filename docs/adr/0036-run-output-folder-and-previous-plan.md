# ADR 0036: 出力を実行の時刻のフォルダへ上書きせずに書き、編成のJSONを前回の編成として受け取る

- 状態: 提案中
- 日付: 2026-11-10

## 背景

要件定義書の分割案の2は、運用者の指定と前回の編成を1つの不変な値として編成の入力に持ち、前回の編成を
画面ができるまでファイルで受け取ることを求めている。ADR 0035は、分割案の2の残りのうち、前回の編成の受け取り、
`output/`の置き方（DAT-008）、総力モードの前回の編成の移動先の欄（FRM-071、旧Q-122）を次のPull Requestへ残した。
利用者は2026-11-10に、出力するたびに`output/<実行の時刻>/`へ編成のMarkdownとJSONを書いて上書きせず、運用者が
共有した回のJSONを`--previous`で明示すると決めていた（旧Q-147）。

それまでのCLIは、2つ目の位置引数で受け取った出力のMarkdownのパスへ上書きで書き、編成のJSONを書かなかった。
前回からの移動の数（FRM-071、FRM-037の⑦）を目的関数に入れるのは分割案の5で、このPull Requestでは使わない。

利用者は2026-11-10に次を決めた（要件定義書の未決事項の20回目）。

1. 位置引数の数は保ち、2つ目を出力のフォルダとして受け取る。毎回`<出力のフォルダ>/<実行の時刻>/`へ
   `チーム編成.md`と`チーム編成.json`を書く。`.md`で終わるパスは、置き方が変わったことを示して入力のエラーに
   する（旧Q-151）
2. 時刻は実行した計算機の現地時刻の`YYYYMMDD-HHMMSS`とし、同じ名前のフォルダがあれば`-2`、`-3`を付ける。
   編成のJSONの`created_at`は時差付きのISO 8601とする。終了コード2、3、4ではフォルダを作らない（旧Q-152）
3. `--previous`は読み込みと照合だけに使う。JSONの形の誤りは入力のエラー（2）とし、今回の参加者一覧にいない人は
   エラーにせず、編成に使わないことと人数だけを名前なしで標準エラーへ示す（旧Q-153）
4. 編成のJSONは、移動の数に要る最小限（所属、出撃開始時刻、応援、待機、別枠）と版を持ち、総力モードの移動先を
   隊と待機・別枠のメンバーごとの任意の欄とする（旧Q-154）

## 判断

### 実行の時刻のフォルダ

- CLIの`main`は時差付きの現在時刻を返す`clock`を受け取る（既定は現地時刻）。テストは固定した時刻を渡す
- 編成が検証を通った後にだけ、`interfaces/cli/run_output.py`が出力のフォルダ（なければ作る）の中に実行の時刻の
  フォルダを`mkdir`で新しく作り、作れたフォルダへ書く。同じ名前があれば番号を上げて作り直すため、前の回の出力を
  上書きしない。作ったフォルダは標準出力に示す。2つのファイルの一方を書けなければ、作ったフォルダを消して
  終了コード2で終える。Markdownだけのフォルダが残ると、完全な回と見分けられなくなるため
- 以前の書き方（`.md`で終わるパス）は、黙ってその名前のフォルダを作ると運用者が出力を見失うため、入力のエラーに
  して新しい置き方を示す
- 出力のフォルダが既にあるファイルを指す場合と確かめられない場合も、最適化の後に知らせると待ち時間が無駄に
  なるため、編成の前に入力のエラーにする。`.md`の判定を先にし、以前の版の出力のファイルが残っていても置き方の
  変化を示す。細部は作成者の仮定A-42の(5)
- 成功を示す標準出力の行は、Windowsで標準出力をリダイレクトして符号化が日本語を表せない場合も、退避して書き、
  書いた回を終了コード0で終える

### 編成の記録と編成のJSON

- ドメインに編成の記録`PlanRecord`（隊`RecordedTeam`、待機と別枠のメンバー`RecordedMember`、応援`SupportRef`）を
  置く。メンバーはDAT-007と同じ名前と同盟の組（`MemberRef`）で指す。検証済みの編成（`ValidatedTeamPlan`）から
  だけ作り（`PlanRecord.from_validated`）、Exporterと同じく未検証の候補を記録しない
- `PlanRecord`は、隊の欠け、隊の番号の重複か1未満、同じメンバーの二重の置き場所、リーダーの欠けと重複、第1〜3隊の出撃開始時刻、成り立たない応援、空の移動先、時差のない
  時刻を拒否する。エラーの文には名前を書かない（ADR 0026）
- JSONの変換は`adapters/persistence/json_plan_record_repository.py`に置く（Repository境界）。書き出し
  （`render_plan_record`）と読み込み（`JsonPlanRecordRepository`）を同じモジュールに置き、書いたJSONを読み戻すと
  同じ記録になることを性質テストで確かめる。版は`schema_version` 1とし、違う版は読み込みエラーにする
- 総力モードの移動先（`destination_alliance`）は、総力モードを加える分割案の7で書く。この版では書かないが、
  読み書きできる

### 前回の編成の受け取り

- `--previous`で渡した記録は、運用者の指定`OperatorSpecification`の`previous_plan`に持たせ、OptimizerとValidatorへ
  同じ値を渡す（分割案の2）。回答を受け入れた指定（`with_late_start`）も同じ値を引き継ぐ
- この版のOptimizerとValidatorは`previous_plan`を使わない。CLIは、編成に使わないことを標準エラーへ注意として
  示す。`TeamBuilder`は今回の参加者一覧に名前と同盟の組で当たらない人数（`PlanRecord.unmatched_count`）を返し、
  CLIは出力した実行（終了コード0）で0人でなければ人数だけを示す（作成者の仮定A-42の(6)）
- 前回の編成は回答を確かめる手順（作成者の仮定A-41）に影響しないため、前回の編成を渡す、変える、外す実行でも
  FRM-090の性質(1)が成り立つ（作成者の仮定A-42の(2)）

## 代替案

- 出力のMarkdownのパスを保ち、`--output-dir`を足したときだけ時刻のフォルダへ書く: 以前の書き方と互換だが、
  付け忘れるとJSONが残らず、「出力するたびに」を満たさないため採用しない（利用者の決定1）
- 出力のパスのファイル名を保ち、親を`output/`とみなす: 書き方は変わらないが、指定したパスに書かれず、READMEの
  例ではカレントに時刻のフォルダができるため採用しない（利用者の決定1）
- 同じ時刻のフォルダがあれば入力のエラーにする: 単純だが、同じ秒の2回目の実行が失敗するため採用しない
  （利用者の決定2）
- `--previous`をまだ足さず、JSONを書くだけにする: 使わない値を受け取る心配はないが、旧Q-147の決定の一部を
  後に回すため採用しない（利用者の決定3）。使わない値を受け取ると効いたと誤解されるおそれ（ADR 0034で未実装の
  キーを読み込みエラーにした理由）は、標準エラーの注意で補う
- 前回の編成の参加者が今回の参加者一覧にいなければ入力のエラーにする: 共有の後に抜けた人がいる再編成
  （FRM-071の用途）で使えなくなるため採用しない（利用者の決定3）
- 編成のJSONにメンバーの参加時間、G、VC、時間帯ごとの出撃も持たせる: JSONだけで編成を再現できるが、移動の数に
  要らず、読み込みの検証が増えるため採用しない（利用者の決定4）
- 前回の編成を`OperatorSpecification`と別の引数でユースケースへ渡す: 運用者の指定の型は変わらないが、分割案の2の
  「1つの不変な値として編成の入力に持ち、OptimizerとValidatorへ同じ値を渡す」に反するため採用しない

## 影響

- CLIの2つ目の引数の契約が変わる。以前の`チーム編成.md`のようなパスを渡す手順や自動化は、出力のフォルダへ
  変える必要がある。`.md`で終わるパスは終了コード2で止まるため、黙って別の場所へ書かない
- 出力のフォルダには実行ごとにフォルダが増える。運用者は不要になった回のフォルダを手で消す
- 編成のJSONは個人名を含む。イベントのフォルダ（Git管理外）に置き、`AGENTS.md`の伏せる語の規則で、本物の
  回答（`answers.json`）とともに、コミット、Pull Request、レビュー結果へ書かない対象に加えた
- 前回からの移動の数（FRM-071、FRM-037の⑦）は分割案の5で目的関数に入れる。そのとき、前回の編成を変えた実行は
  回答以外の運用者の指定を変えた実行として、作成者の仮定A-41の(5)の手順で確かめる
- 総力モードの移動先の欄は、総力モード（分割案の7）で書き、移動の数に数える
- 分割案の2はこのPull Requestで終わる
