# ADR 0003: 戦術的DDDの段階導入

- 状態: 採用
- 日付: 2026-07-19

## 背景

現行実装には不変ドメインモデル、Repository、アプリケーション相当のService、独立Validatorが
ある。一方、パッケージは`models`、`optimizer`、`cli`など技術レイヤー名で分かれ、境界が
`cli.service`に置かれている。Web UIや永続化方式を増やす前に、業務ルールの所在と依存方向を
明確にする必要がある。

## 判断

- 「KvKチーム編成」を唯一のコアドメインかつ境界づけられたコンテキストとする
- モジュラーモノリスのまま、ドメイン、アプリケーション、アダプター、Interfaceの境界を設ける
- Markdown、JSON、CLI、OR-Toolsをドメインの外側に置く
- アプリケーションのユースケースはドメイン型を受け取り、検証済み結果を返して入出力形式を
  扱わない
- `Member`、`TimeSlot`、`TeamMaster`など現在の用語をユビキタス言語の基準にする
- 未検証の`DynamicTeamPlan`と出力可能な`ValidatedTeamPlan`を段階的に型で分ける
- 既存動作を維持し、パッケージ再編は機能変更と分離して段階的に行う
- ドメインから外側への依存を防ぐ自動検査はパッケージ移行後に品質ゲートへ追加する

## 代替案

### 現在の技術レイヤー構造を維持する

小規模な間は単純だが、CLI、Web、ソルバー、永続化が増えると業務ルールの所在と依存方向が
曖昧になるため採用しない。

### 全コードを一度にDDD構造へ移す

差分が大きくなり、import変更と振る舞い変更の原因を分離できないため採用しない。

### コンテキストごとにマイクロサービス化する

現時点では独立した言語モデル、Deployment、拡張性要件がなく、運用負荷だけが増えるため
採用しない。

### CQRSとイベントソーシングを導入する

履歴再生や独立した参照モデルの要件がないため採用しない。

## 影響

業務ルールの配置判断と用語が明確になる一方、移行期間は現行構造と目標構造が併存する。
Pull Requestを小さく保ち、各段階で公開CLI、生成Markdown、全テストを維持する必要がある。
