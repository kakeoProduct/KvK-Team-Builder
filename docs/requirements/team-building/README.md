# KvKチーム編成 要件定義書

本書は、境界づけられたコンテキスト「KvKチーム編成」（`team_building`）の目標仕様である。利用者が
運用で使っている2つのルール文書（同盟メンバー表の整形ルール、チーム編成ロジック v2と2026-10-10の
確定分）を、要件ID付きで書き起こした。

## 1. 位置付け

- 本書は編成ルールの**目標仕様の正本**である（ADR 0023）
- 現行の実装（リーダー一覧から作る所属固定の隊と、回答で受け取る遅れて出撃する隊と応援。選択肢の提示、FRM-037の目的関数などは未実装。ADR 0034、ADR 0035）は、`README.md`と`AGENTS.md`の
  「現行のプロダクトルール」が説明する。実装Issueが完了するたびに、該当する要件をREADME、
  AGENTS、architecture、domain-modelへ反映し、現行の記述を置き換える
- 運用値（戦闘時間、隊の数、リーダー、人数の上限、総力の最低ライン、
  呼び名の対応、同盟の顔ぶれとグループ分け、移動後の同盟の人数の上限と総力の目標、協力者同盟、
  移動先が分かれてよい同盟）は毎回変わる設定であり、本書には値を書かず
  「設定値」と定める。利用者が決めた値は[未決事項](open-questions.md)の「決定済みの事項」に記録する
- 設定値のうち、Repositoryで管理するものと、実行ごとの入力または永続化（#2）に置くものの区別は、
  実装Issueの1と2で決める。それまで置き場所を確定しない。ただし、個人名を含む運用者の指定（リーダー一覧、
  メンバーへの指定）は、ADR 0029とDAT-007に従いバージョン管理の対象外に置く。実装Issueの2（ADR 0034）では、
  リーダー一覧をイベントのフォルダの`settings.json`に、戦闘時間と第4隊以降の上限の常設の既定値をRepositoryの
  チームマスタに置いた。戦闘時間は毎回変わるため、イベントごとの上書き（DAT-007の`battle_start`、`battle_end`）は、
  ROS-020を扱う実装Issueの1で`settings.json`から読めるようにする。それまでは、チームマスタを`--team-master`で
  差し替えて戦闘時間を変える（作成者の仮定A-40。ADR 0034）
- 利用者が決めた固定値は、毎回変わる運用値ではない。対象は次のとおり。戦闘開始の20:00か21:00、
  序盤の戦闘開始から1時間、延長境界時刻の24:00、上位隊の3隊と各8人（固定をなくさない）、
  出撃人数の下限8人、7人を警告とする境界、6人以下の禁止（FRM-046の例外あり）、隊ごとの上限の
  上書きの範囲8〜9人、応援先を第5隊以降とすること、◆が1〜2人の境界、30分単位の時間帯、
  「その他」をG4とすること、1ブロックの改行10個、治療時間の4分。運用値をPythonへ直書きしない規則（AGENTS）との関係と置き場所（ドメインの
  定数か、固定の設定か）は、実装Issueの1でADRに決める。ただし、利用者の決定（2026-11-09）により実装Issueの2を
  先に進めたため、上位隊の3隊と各8人、出撃人数の下限8人、延長境界時刻、30分単位の時間帯はADR 0034で
  ドメインの定数とした。序盤の戦闘開始から1時間と、応援先を第5隊以降とすることは、ADR 0035で同じくドメインの
  定数とした。ほかの固定値は、それを使う実装Issueで同じ置き場所にする
- 実運用の参加者名と同盟名は本書とテストへ含めない。例は架空の名前で示す。実運用の個人名を含むデータは
  バージョン管理の対象外に保持し、Repositoryには形式だけを[data-formats.md](data-formats.md)に定める（ROS-055、ADR 0029）
- 元のルール文書の中で、新しい規則（v2、2026-10-10確定分）と古い規則が食い違う場合は、新しい方を
  採用する（元文書の指示による）。利用者の決定はそれより優先する

### 2.1 要件の分類

各要件には、`$change-kvk-rules`の分類に、非機能と廃止を加えた分類を付ける。

| 分類 | 意味 |
|---|---|
| 必須条件 | 満たせない編成を出力しない。Validatorが1つの編成について判定する。選択肢の範囲など最適化の結果に頼る条件は、アプリケーションが確かめる（FRM-047、FRM-090） |
| 警告 | 編成を出力し、不足を運用者へ知らせる |
| 目的関数 | 複数の有効な編成から望ましいものを選ぶ。指標と優先順位を付ける（FRM-037） |
| 入力正規化 | 参加者の記述をドメインの値へ変換する、または曖昧な入力を確認に回す |
| 運用操作 | 運用者の指定（FIX、セット、移動など）を受けて編成を変える |
| 表示のみ | 編成の有効性を変えずに出力や画面を変える |
| 非機能 | 複数回の実行にまたがる性質など、1つの編成では判定できない要件。決まった検証方法で確かめる |
| 廃止 | 利用者の決定などで採用しないことにした要件 |

## 3. 用語

| 用語 | 意味 | 現行の用語との対応 |
|---|---|---|
| 隊 | 所属が固定されたメンバーの集まり。第1隊から番号を振る | `TeamMembership`（番号は`int`） |
| リーダー | 隊を率いるメンバー。リーダー一覧の番号が隊の番号になる | `TeamMembership.leader`、リーダー一覧は`OperatorSpecification.leaders` |
| 代理リーダー | リーダーが遅れる、抜ける時間帯にリーダーとして扱うメンバー。当面、アプリは決めない（FRM-003） | なし（以前の代理集結主`SubstituteLeader`は廃止した。ADR 0034） |
| 上位隊 | 第1〜3隊。リーダーを含めて8人固定で、全時間帯の入れ替えがない。固定をなくさない（FRM-026） | `is_top_team`、`TOP_TEAM_COUNT`、`TOP_TEAM_SIZE` |
| 所属 | メンバーが属する隊。時間帯をまたいで変わらない | `TeamMembership.members` |
| 稼働 | ある時間帯に参加していること | `Availability` |
| 出撃人数 | ある時間帯に隊として出撃する人数。所属メンバーのうち稼働している人と、応援に来た人の合計 | `Sortie.head_count` |
| 応援 | 遅れて出撃する隊の所属メンバーが、出撃開始前にほかの隊で出撃すること | `Support`（`TeamPlan.supports`）、運用者の指定は`SupportRef` |
| 出撃開始時刻 | 隊が出撃を始める時刻。遅れて出撃する隊は戦闘開始より後になる | `TeamMembership.start_minutes`、運用者の指定は`LateStart` |
| 序盤 | 戦闘開始からの1時間。20:00に始まる回は20:00〜21:00、21:00に始まる回は21:00〜22:00（FRM-040） | `is_opening`、`OPENING_MINUTES` |
| 休止 | 出撃開始後に、所属メンバーの参加が0人になる時間帯。24時より前は6人以下と同じく扱う（FRM-048） | `ValidationCode.REST` |
| 延長境界時刻 | 人数不足を延長保留として扱い始める時刻。24:00で固定する | `EXTENSION_BOUNDARY_MINUTES` |
| 時間帯 | 30分単位の区間。戦闘時間を区切る | `TimeSlot` |
| 別枠 | 隊に入れないメンバーの区分。参加時間未定のメンバーを置く | `TeamPlan.undecided`（以前の待機`Standby`に当たる） |
| 待機 | 人数の上限のため、または運用者の指定（FRM-076）で、どの隊にも所属しないメンバー | `TeamPlan.waiting`（運用者の指定は未実装）。以前の`Standby`とは別の概念 |
| G | 兵士レベル。G8〜G5は数値のまま、「その他」はG4として計算する | `Tier` |
| ◯／△／◇／◆ | マンスリー持ち／途中抜け／VC参加可能（聴き専可）／ビビアン星4以上持ち（以前の表記は★） | ◆は新しい概念 |
| 総力 | 拳マークの数値（例: 491.3M）。総力モードでだけ使う | なし |
| グループ | 複数の隊をまとめた単位で、移動先の同盟を1つ持つ。通常モードと総力モードで同じ概念とする（旧Q-139）。総力モードでは同盟もまとめ、FRM-081〜FRM-086の対象になる。通常モードでは運用者が編成の前に渡すか編成の後に画面で作り、応援先の制限、同じグループにしたい組、治療時間の目安、同盟の移動人数に使う（FRM-004、FRM-110〜FRM-112、UI-013） | なし |
| 移動先の同盟 | グループのメンバーが移る同盟。グループごとに1つ（FRM-083、FRM-100、FRM-110）。通常モードでは、同盟の移動人数と、待機と参加時間未定のメンバーの同じグループにしたい組の判定に使う（FRM-077、FRM-112） | なし |
| 同じグループにしたい組 | 運用者ができれば同じグループにしたいと指定した2人の組。グループがある通常モードの目的関数で、別のグループになる組を減らす（FRM-077）。同じ隊に置くセットとは別の指定 | なし |
| 同盟移動協力者 | 隊に入らず、移動先の同盟へ移ってグループに登録し、総力の合計と移動後の同盟の人数に数えるメンバー。グループの人数には数えない（FRM-087、FRM-103）。今の同盟が移動先と同じ協力者は、移さずに登録だけし、入るメンバーに数えない（作成者の仮定A-28） | なし |
| 協力者同盟 | 総力モードで、全員を同盟移動協力者として読む1同盟。運用者が設定で指定する（ROS-007） | なし |
| 登録 | 総力モードで、グループの一員として移動先の同盟へ移すこと（今の同盟が移動先と同じ人は移さずに登録だけする）。隊のメンバー、待機、参加時間未定、協力者を含む（OUT-017） | なし |
| FIX | 運用者が動かさないと指定した隊 | なし |
| セット | 運用者が同じ隊に置くと指定したメンバーの組 | なし |

## 5. 実装Issueの分割案

`$change-kvk-rules`で次の順に実装する。各Issueは#5の子とする。どのIssueも、公開CLIを維持し、
必須条件の抜けた編成を出力しない。新しい契約に置き換わる現行のテストは、置き換えるIssueで新しい
期待値へ更新し、変更理由を示す。テストを削除、スキップ、弱体化しない（`AGENTS.md`の変更手順）。

| 順 | Issue案 | 主な要件 | 備考 |
|---|---|---|---|
| 1 | 入力の拡張（参加時間の読み方、記号◆、兵種、時刻のない途中参加） | ROS-001〜ROS-042、ROS-060 | Parserと入力正規化。設定値の置き場所（1章）を決める。利用者の決定（2026-11-09）により2を先に進め、2が使う固定値（30分単位を含む）の置き場所はADR 0034で決めた。`settings.json`の`battle_start`と`battle_end`を読み、チームマスタの戦闘時間の既定値を上書きする（ROS-020、DAT-007、作成者の仮定A-40） |
| 2 | 所属固定のモデル、隊・リーダー、応援と出撃開始時刻、別枠と待機、運用者の指定（総力モードの協力者の欄の移動先と同盟の選択を含む） | FRM-001〜FRM-004、FRM-010〜FRM-013、FRM-041、FRM-042、FRM-047、FRM-048、FRM-060〜FRM-062 | 2〜3件のPull
