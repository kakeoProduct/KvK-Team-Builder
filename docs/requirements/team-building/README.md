# KvKチーム編成 要件定義書

本書は、境界づけられたコンテキスト「KvKチーム編成」（`team_building`）の目標仕様である。利用者が
運用で使っている2つのルール文書（同盟メンバー表の整形ルール、チーム編成ロジック v2と2026-10-10の
確定分）を、要件ID付きで書き起こした。

## 1. 位置付け

- 本書は編成ルールの**目標仕様の正本**である（ADR 0023）
- 現行の実装（A〜Kの11隊固定、時間帯ごとのチーム移動あり）は、`README.md`と`AGENTS.md`の
  「現行のプロダクトルール」が説明する。実装Issueが完了するたびに、該当する要件をREADME、
  AGENTS、architecture、domain-modelへ反映し、現行の記述を置き換える
- 運用値（戦闘時間、隊の数、リーダー、人数の上限、総力の最低ライン、
  呼び名の対応、同盟の顔ぶれとグループ分け、移動後の同盟の人数の上限と総力の目標、協力者同盟、
  移動先が分かれてよい同盟）は毎回変わる設定であり、本書には値を書かず
  「設定値」と定める。利用者が決めた値は[未決事項](open-questions.md)の「決定済みの事項」に記録する
- 設定値のうち、Repositoryで管理するものと、実行ごとの入力または永続化（#2）に置くものの区別は、
  実装Issueの1と2で決める。それまで置き場所を確定しない。ただし、個人名を含む運用者の指定（リーダー一覧、
  メンバーへの指定）は、ADR 0029とDAT-007に従いバージョン管理の対象外に置く
- 利用者が決めた固定値は、毎回変わる運用値ではない。対象は次のとおり。戦闘開始の20:00か21:00、
  序盤の戦闘開始から1時間、延長境界時刻の24:00、上位隊の3隊と各8人（固定をなくさない）、
  出撃人数の下限8人、7人を警告とする境界、6人以下の禁止（FRM-046の例外あり）、隊ごとの上限の
  上書きの範囲8〜9人、応援先を第5隊以降とすること、◆が1〜2人の境界、30分単位の時間帯、
  「その他」をG4とすること、1ブロックの改行10個、治療時間の4分。運用値をPythonへ直書きしない規則（AGENTS）との関係と置き場所（ドメインの
  定数か、固定の設定か）は、実装Issueの1でADRに決める
- 実運用の参加者名と同盟名は本書とテストへ含めない。例は架空の名前で示す。実運用の個人名を含むデータは
  バージョン管理の対象外に保持し、Repositoryには形式だけを[data-formats.md](data-formats.md)に定める（ROS-055、ADR 0029）
- 元のルール文書の中で、新しい規則（v2、2026-10-10確定分）と古い規則が食い違う場合は、新しい方を
  採用する（元文書の指示による）。利用者の決定はそれより優先する

### 2.1 要件の分類

各要件には、`$change-kvk-rules`の分類に、非機能と廃止を加えた分類を付ける。

| 分類 | 意味 |
|---|---|
| 必須条件 | 満たせない編成を出力しない。Validatorが1つの編成について判定する。選択肢の範囲など最適化の結果に頼る条件は、アプリケーションが確かめる（FRM-047、FRM-090） |
| 警告 | 編成を出力し、不足を運用者へ知らせる |
| 目的関数 | 複数の有効な編成から望ましいものを選ぶ。指標と優先順位を付ける（FRM-037） |
| 入力正規化 | 参加者の記述をドメインの値へ変換する、または曖昧な入力を確認に回す |
| 運用操作 | 運用者の指定（FIX、セット、移動など）を受けて編成を変える |
| 表示のみ | 編成の有効性を変えずに出力や画面を変える |
| 非機能 | 複数回の実行にまたがる性質など、1つの編成では判定できない要件。決まった検証方法で確かめる |
| 廃止 | 利用者の決定などで採用しないことにした要件 |

## 3. 用語

| 用語 | 意味 | 現行の用語との対応 |
|---|---|---|
| 隊 | 所属が固定されたメンバーの集まり。第1隊から番号を振る | `Team`（現行は時間帯ごとに移動できる） |
| リーダー | 隊を率いるメンバー。リーダー一覧の番号が隊の番号になる | 固定集結主（`RallyLeader`）に当たる候補 |
| 代理リーダー | リーダーが遅れる、抜ける時間帯にリーダーとして扱うメンバー。当面、アプリは決めない（FRM-003） | 代理集結主（`SubstituteLeader`）に当たる候補 |
| 上位隊 | 第1〜3隊。リーダーを含めて8人固定で、全時間帯の入れ替えがない。固定をなくさない（FRM-026） | A〜C |
| 所属 | メンバーが属する隊。時間帯をまたいで変わらない | なし（新しい概念） |
| 稼働 | ある時間帯に参加していること | `Availability` |
| 出撃人数 | ある時間帯に隊として出撃する人数。所属メンバーのうち稼働している人と、応援に来た人の合計 | 時間帯ごとのチーム人数 |
| 応援 | 遅れて出撃する隊の所属メンバーが、出撃開始前にほかの隊で出撃すること | なし（新しい概念） |
| 出撃開始時刻 | 隊が出撃を始める時刻。遅れて出撃する隊は戦闘開始より後になる | なし（新しい概念） |
| 序盤 | 戦闘開始からの1時間。20:00に始まる回は20:00〜21:00、21:00に始まる回は21:00〜22:00（FRM-040） | なし |
| 休止 | 出撃開始後に、所属メンバーの参加が0人になる時間帯。24時より前は6人以下と同じく扱う（FRM-048） | なし |
| 延長境界時刻 | 人数不足を延長保留として扱い始める時刻。24:00で固定する | なし |
| 時間帯 | 30分単位の区間。戦闘時間を区切る | `TimeSlot` |
| 別枠 | 隊に入れないメンバーの区分。参加時間未定のメンバーを置く | 現行の待機（`Standby`）に当たる |
| 待機 | 人数の上限のため、または運用者の指定（FRM-076）で、どの隊にも所属しないメンバー | なし。現行の`Standby`とは別の概念で、流用しない |
| G | 兵士レベル。G8〜G5は数値のまま、「その他」はG4として計算する | `Tier` |
| ◯／△／◇／◆ | マンスリー持ち／途中抜け／VC参加可能（聴き専可）／ビビアン星4以上持ち（以前の表記は★） | ◆は新しい概念 |
| 総力 | 拳マークの数値（例: 491.3M）。総力モードでだけ使う | なし |
| グループ | 複数の隊をまとめた単位。総力モードでは同盟もまとめ、FRM-081〜FRM-086の対象になる。通常モードでは運用者が画面で作り、治療時間の目安の計算だけに使う（FRM-004、UI-013） | なし |
| 移動先の同盟 | 総力モードで、グループのメンバーが移る同盟。グループごとに1つ（FRM-083、FRM-100） | なし |
| 同盟移動協力者 | 隊に入らず、移動先の同盟へ移ってグループに登録し、総力の合計と移動後の同盟の人数に数えるメンバー。グループの人数には数えない（FRM-087、FRM-103）。今の同盟が移動先と同じ協力者は、移さずに登録だけし、入るメンバーに数えない（作成者の仮定A-28） | なし |
| 協力者同盟 | 総力モードで、全員を同盟移動協力者として読む1同盟。運用者が設定で指定する（ROS-007） | なし |
| 登録 | 総力モードで、グループの一員として移動先の同盟へ移すこと（今の同盟が移動先と同じ人は移さずに登録だけする）。隊のメンバー、待機、参加時間未定、協力者を含む（OUT-017） | なし |
| FIX | 運用者が動かさないと指定した隊 | なし |
| セット | 運用者が同じ隊に置くと指定したメンバーの組 | なし |

## 5. 実装Issueの分割案

`$change-kvk-rules`で次の順に実装する。各Issueは#5の子とする。どのIssueも、公開CLIを維持し、
必須条件の抜けた編成を出力しない。新しい契約に置き換わる現行のテストは、置き換えるIssueで新しい
期待値へ更新し、変更理由を示す。テストを削除、スキップ、弱体化しない（`AGENTS.md`の変更手順）。

| 順 | Issue案 | 主な要件 | 備考 |
|---|---|---|---|
| 1 | 入力の拡張（参加時間の読み方、記号◆、兵種、時刻のない途中参加） | ROS-001〜ROS-042、ROS-060 | Parserと入力正規化。設定値の置き場所（1章）を決める |
| 2 | 所属固定のモデル、隊・リーダー、応援と出撃開始時刻、別枠と待機、運用者の指定（総力モードの協力者の欄の移動先と同盟の選択を含む） | FRM-001〜FRM-004、FRM-010〜FRM-013、FRM-041、FRM-042、FRM-047、FRM-048、FRM-060〜FRM-062 | 現行の`DynamicTeamPlan`を置き換え、Validator、`ValidatedTeamPlan`、既存のMarkdown出力を同じIssueで新モデルへ移す。現行の必須条件（A〜Cの8人・VC・戦力関係）は3まで維持する。ただし、リーダー不在の時間帯の7人（FRM-020、FRM-029）は2から許す。運用者の指定（応援先、遅れて出撃する隊と出撃開始時刻、上限超えと下限未満の明示的な許容（許したときの人数を含む。人数だけの上限超えを含む）、隊数を減らす選択、常時参加が怪しいメンバー、FIX、セット、隊への固定と待機の指定（FRM-076）、総力モードの切り替えと同盟のグループ振り分け、移動先の個別指定、移動先が分かれてよい同盟、別の同盟へ移す組、協力者同盟、協力者の欄の移動先、ROS-053の同盟の選択）と前回の編成を、1つの不変な値として編成の入力に持ち、OptimizerとValidatorへ同じ値を渡す。Validatorは指定そのものの妥当性も確かめる（FRM-047）。FRM-047の各条件は、その指定を加えるIssueで実装する。前回の編成は、画面ができるまでファイルで受け取り、JSONの処理はRepository境界に置く。型の枠は2で作り、各指定は要件のあるIssue（3〜7）で加える。Optimizerの結果は、解あり、解がないことの証明、時間切れの3つに分ける。解ありには最適性を示せたかを持たせ、FRM-049で使えるようにする。理由と選択肢を返す結果型は、指定が足りない場合と、解がないことを証明した場合にだけ使う。時間切れは従来どおり時間切れのエラーとして返し、選択肢に変えない（ADR 0019）。理由と選択肢はドメインまたはアプリケーションで作り、問い合わせは再試行しない。FRM-090の選択肢を加える3と4までは、下限に満たない場合は選択肢を示さずに理由を示して出力を止める。選択肢の列挙と隊数を減らす繰り返しで、1回でも探索が時間切れになるか最適性を示せなければ、全体を時間切れのエラーとし、0件や解なしとして扱わない（ADR 0019、FRM-090）。画面ができるまで、CLIは番号付きの質問（FRM-075）を表示し、入力のエラーとは別の終了コードで終える。運用者は回答をファイルまたはオプションで次の実行へ渡す。回答には質問の番号ではなく、問いの対象の（隊、時間帯）と指定そのもの（隊、時間帯、メンバー、応援先など）を書き、アダプターは形式の変換だけを行う。回答を確かめる手順（Issue 4と分担する。旧Q-092）と、FRM-090の性質のテストの枠は、このIssueで決め、テストとADRに記録する。これらをarchitectureとADRに記録する。前回の編成を`output/`に上書きして失わない置き方（DAT-008）、総力モードの前回の編成に待機と参加時間未定のメンバーの移動先も持たせること（FRM-071、旧Q-122）、`settings.json`の値を運用者が渡した指定と常設の既定値のどちらとして扱うか（11章の前文）も、ここで決める |
| 3 | 上位隊、第4隊以降の人数、目的関数の優先順位、結果の再現性、下限未満の明示的な許容 | FRM-005、FRM-020〜FRM-039、FRM-046、FRM-049、FRM-090の場合3〜5 | #41を吸収する。FRM-038のため、ADR 0019（既定の探索設定を変えない）の見直しをADRで決める。場合3〜5の選択肢を加えるときに、FRM-090の性質(1)〜(6)とA-10の例3のテストを足す。総力モードの指標（FRM-104）を重み付きの目的関数に組むときに、総力の桁があふれないかをADRで確かめる |
