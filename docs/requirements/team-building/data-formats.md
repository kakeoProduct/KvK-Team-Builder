# 要件定義: 個人名を含むデータの保持形式

実運用の参加者名を含むデータを、バージョン管理の対象外に保持するときの置き場所と形式を定める（ROS-055、
ADR 0029）。Repositoryには本書の形式と架空の例だけを置き、実際の値は置かない。例の名前、同盟、ID、
数値はすべて架空で、既定値ではない。置き場所、ファイル形式、列とキーの名前は作成者が決めた（作成者の仮定A-23）。

## 1. 置き場所と共通の規則

| ID | 分類 | 要件 |
|---|---|---|
| DAT-001 | 非機能 | 個人名を含むデータは、イベントごとのフォルダにまとめて置く。既定はメインの作業ツリーの`tmp/events/<開催日>-<イベント名>/`（`.gitignore`の`/tmp/`の対象）とし、運用者はRepositoryの外のフォルダを指定してもよい。アプリはイベントのフォルダをパスで受け取り、イベント名から作らない。Session用のworktreeの`tmp/`には置かない（worktreeを削除すると消えるため）。コミット、Pull Request、Issue、レビュー結果へ実際の値を転記しない（ADR 0024）。検証は、`.gitignore`が`/tmp/`を対象にしていることを構造テスト（`tests/test_ai_harness.py`）で確かめる |
| DAT-002 | 非機能 | イベントのフォルダのテキストファイル（`roster.txt`、CSV、`settings.json`、`answers.json`、`output/`の隊のファイルと編成のJSON）はUTF-8とする。書き出しはBOMなしとし、読み込みはBOMの有無の両方を受け付け、UTF-8として読めないファイルはファイル名と行を示して入力のエラーとする（作成者の仮定A-23）。表形式のデータはCSVとし、1行目に列名を書く。列名は本書の英語の識別子を使う。取得時刻などの時刻の値（`fetched_at`、`checked_at`、`roster_received_at`）は時差付きのISO 8601で書く。時差のない時刻は、ファイル名と行（JSONではキー）を示して入力のエラーとする。`power_snapshot.csv`と`alliance_roster.csv`のそれぞれの中で（`alliance_roster.csv`は同じ同盟の中で）、照合した結果（A-29のまとまりを含む）が同じメンバーの行が同じ取得時刻で2行以上ある場合も同じとする。`alliance_roster.csv`で同盟の違う行に同じメンバーが同じ取得時刻で載る場合も、所属を決められないため同じとする。取得時刻が違えば、最も新しい行の同盟の名簿にだけ数える。`game_id`が空欄の行は、名前の対応表で`game_id`を補ってから同じメンバーかを決め、補えなければ、同じ同盟の中だけで`game_name`が同じIDのない行どうしを同じメンバーとし、IDのある行とのまとめ方はA-29による。照合の件数も、このまとまりで数える（旧Q-123、作成者の仮定A-29）。`name_map.csv`は、1人の別名で同じ`game_id`の行が複数あってよく、`roster_name`のある行で同じ`roster_name`と`alliance`が別の`game_id`を指す場合と、`roster_name`が空欄の行で同じ`game_name`と`alliance`が別の`game_id`を指す場合だけを入力のエラーとする。同じ`roster_name`と`alliance`で`game_id`のある行と空欄の行が並ぶ場合はエラーにせず、A-29でまとめた結果に従う。1つのまとまりになれば照合でき、2つ以上のまとまりに当たれば照合できないとして確認に回す（作成者の仮定A-28）。どの取得元のデータにも、取得元と取得時刻の列を持たせる |
| DAT-003 | 非機能 | 取得元は`external_site`（外部の集計サイト）、`screenshot`（スクリーンショットからの読み取り）、`manual`（運用者の入力）のいずれかで書く。外部の集計サイトが使えなくなっても、ほかの2つの取得元で同じ形式のデータを作れるようにする（ROS-051、ROS-053）。ゲーム内のIDが分からない場合は`game_id`を空欄にしてよく（`power_snapshot.csv`と`alliance_roster.csv`の`external_site`の行を除く。DAT-006。名前の対応表の行は取得元によらず空欄にしてよい。作成者の仮定A-26）、ゲーム内名は変わり得て一意ではなくなるため（旧Q-126）、名前の対応表（Git管理外）で今のIDと対応させるのを原則とし（旧Q-123）、補えないメンバーは作成者の仮定A-29で照合し、2件以上に当たって1人に決まらなければROS-060で確認に回す（0件の扱いは作成者の仮定A-28） |

## 2. 入力データ

| ID | 分類 | 要件 |
|---|---|---|
| DAT-004 | 入力正規化 | 参加者一覧は、運用者から受け取ったテキストのまま`roster.txt`に保存する。書き方はROS-001〜ROS-033に従う |
| DAT-005 | 入力正規化 | 名前の対応表（ROS-006）は`name_map.csv`とし、列は`roster_name`（参加者一覧の記載）、`game_name`（ゲーム内名）、`game_id`（ゲーム内のID）、`alliance`（参加者一覧の同盟）、`source`、`checked_at`とする。編成に参加しないメンバーの今のIDを持つため、`roster_name`を空欄にした行を書いてよい。その行の`alliance`は、確かめた時点のゲーム内の同盟とする（旧Q-123、作成者の仮定A-29）。このファイルはイベントのフォルダに置き、次のイベントでは前回のファイルを写して直す |
| DAT-006 | 入力正規化 | 総力とMystic Trialは`power_snapshot.csv`とし、列は`game_id`、`game_name`、`alliance`、`power`（総力。整数。未取得は空欄）、`mystic_trial`（Mystic Trialのスコア。未取得は空欄）、`source`、`fetched_at`とする。同盟の名簿（ROS-054）は`alliance_roster.csv`とし、列は`alliance`、`game_id`、`game_name`、`power`（未取得は空欄）、`source`、`fetched_at`とする。編成に参加しないメンバーも1行ずつ含める。外部の集計サイトのアダプターは、取得を指示した範囲（取得の単位）のデータをすべて取得できたときだけファイルを書く。取得の単位は、同盟の名簿では同盟、総力とMystic Trialでは同盟か順位表の上位N人とする。通信の失敗、応答の途中切れ、ページの欠けは一部だけの取得とし、ファイルを書かずにROS-053に従って止める。同盟の単位で0行の応答と、0行の順位表と、取得元が一覧の終わりを示さずにN人未満で終わった順位表も、一部だけの取得とする。同盟を移った人が、移った先の同盟を取り直すまで総力の未取得になることは許す（旧Q-124）。外部の集計サイトの名簿の行は`game_id`が欠けない（旧Q-127）。総力のデータの`external_site`の行も欠けないとみなし（順位表の応答は保持しているデータのとおり。旧Q-128）、`source`が`external_site`の行で`game_id`が空欄なら、取得の誤りとしてファイルを書かずに止める。手で直したファイルを読むときも、`external_site`の行で`game_id`が空欄なら、ファイル名と行を示して入力のエラーとする。止めた後の扱いはROS-053の取得の失敗と同じとする（作成者の仮定A-26）。取得元に記録がないメンバーは一部だけの取得に当たらず、行を書かずに未取得とする（作成者の仮定A-26）。新しいファイルは、取得した行と、置き換える前のファイルにある単位の外の行から作る。単位の中の前の行（`alliance_roster.csv`では取得した同盟の行すべて、`power_snapshot.csv`では、同盟で取得したならその同盟の、順位表で取得したならすべての同盟の`source`が`external_site`の行）は引き継がず、それ以外の行は書き換えずにそのまま残す。書くときに同じメンバーの行をまとめない。アダプターは行を取得元、取得時刻、ファイル名と行とともに不変な値として渡し、1人1つの値はドメインでROS-050とA-28により決める。複数のファイルの置き換えが途中で失敗しても、新しいファイルと古いファイルを混ぜて編成に使わず、ファイル名を示して止める。置き換えが失敗した後でも、同じ単位の取り直しに成功すれば、その結果を編成に使える。置き換えの方法（一時ファイル、退避、戻し）は実装Issueの7のADRで決める（作成者の仮定A-26）。行がないメンバーは未取得として扱うため、途中で切れたファイルを正常なデータとして残さない |
| DAT-007 | 運用操作 | 個人名を含む運用者の指定は`settings.json`とする。メンバーは`{"name": 参加者一覧の名前, "alliance": 参加者一覧の同盟}`の形で指す。同盟は`alliance_choices`を当てる前の、参加者一覧に書かれた同盟とする（作成者の仮定A-28）。キーは`leaders`（リーダーの順の一覧）、`pin_team`（メンバーと隊の番号の組の一覧、FRM-076(1)）、`force_wait`と`optional_wait`（メンバーの一覧、FRM-076(2)(3)）、`apart_pairs`（2人の組の一覧、FRM-105）、`together_pairs`（同じグループにしたい2人の組の一覧、FRM-077）、`default_destination_alliance`（通常モードの待機と参加時間未定の既定の移動先の同盟、FRM-112）、`destination_overrides`（メンバーと移動先の同盟の組の一覧、FRM-101(1)。通常モードではFRM-112(1)）、`alliance_choices`（ROS-053の確認で運用者が選んだ同盟。メンバーと同盟の組の一覧、作成者の仮定A-28）とする。ほかの設定値（戦闘時間、人数の上限、グループ、協力者同盟、移動先が分かれてよい同盟、総力の目標など）の置き場所は実装Issueの1と2で決め、それまでは同じファイルに置いてもよい。その場合の形は4章の例による。ただし現行の実装（ADR 0034）は`leaders`だけを読み、戦闘時間と第4隊以降の上限はRepositoryのチームマスタに置く。実装していないキー（4章の例の`battle_start`、`battle_end`、`roster_received_at`などを含む）は、効いたと誤解しないよう、黙って無視せずキーを示して読み込みエラーにする。キーは、それを使う実装Issueで読めるようにする。戦闘時間はチームマスタを常設の既定値とし、イベントごとの上書き（`battle_start`、`battle_end`）は実装Issueの1（ROS-020）で読めるようにする。それまでは`--team-master`で差し替える（作成者の仮定A-40）。参加者一覧を受け取った時刻は`roster_received_at`（時差付きのISO 8601）とし、参加者一覧の記載の総力を使う場合（ROS-050）に必須とする（作成者の仮定A-27）。協力者の欄の協力者の移動先（FRM-087）は、`{"alliance": 参加者一覧の同盟, "destination_alliance": 移動先の同盟}`の一覧の`cooperator_destinations`とする。書ける値と誤りの扱いは作成者の仮定A-28による。協力者同盟（ROS-007）は1件だけの`cooperator_alliance`とし、グループの隊は`{"first": 最初の隊, "last": 最後の隊}`の範囲で書く。通常モードのグループ（FRM-110）は、隊を番号の一覧（例: `[1, 3, 4]`）でも書ける。総力モードで一覧の形を書いた場合は、キーと値を示して入力のエラーとする（作成者の仮定A-30） |
| DAT-009 | 運用操作 | 番号付きの質問（FRM-075）への運用者の回答は`answers.json`とし、`--answers`で渡す。`settings.json`とは分ける（利用者の決定、2026-11-10）。キーは`answers`（回答の一覧）だけとし、1件の回答は`target`（問いの対象。`team`は隊の番号、`time`は時間帯の開始時刻）と`late_start`（遅れて出撃させる隊の`team`、出撃開始時刻の`start`、出撃開始前の応援の一覧の`support`）を持つ。`support`の1件は、`member`（DAT-007と同じ`{"name": 参加者一覧の名前, "alliance": 参加者一覧の同盟}`の形）、`time`（応援する時間帯の開始時刻）、`team`（応援先の隊の番号）とする。応援のない遅れて出撃する隊では`support`を省ける。質問の番号は書かない。`target`は序盤（戦闘開始からの1時間）の問いの対象とし、序盤以外の対象は入力のエラーとする（遅れて出撃させる案は序盤の選択肢のため。FRM-041、FRM-047）。回答の中の順は結果に影響しない。未知のキーと型の誤りは、名前を書かずに位置とキーを示して読み込みエラーにする。回答を確かめる手順は作成者の仮定A-41による。この版の回答は遅れて出撃させる案だけで、隊数を減らす（FRM-005）と明示して許す（FRM-046）のキーは分割案の3と4で加える |

## 3. 出力データ

| ID | 分類 | 要件 |
|---|---|---|
| DAT-008 | 表示のみ | 編成結果とチャット共有用テキストは、イベントのフォルダの`output/`に置く。グループがある総力モードでは、チャット共有用テキストを2つのファイルに分ける。通常モードとグループのない総力モードでは隊のファイルだけを書き、隊の一覧はそのモードの形（通常モードはOUT-001〜OUT-004、グループがある通常モードはグループごとにまとめたOUT-019、総力モードはOUT-015）とする（作成者の仮定A-23、旧Q-137）。隊のファイルには、グループのない総力モードの総力の取得元と取得日の行（OUT-015）、隊ごとの一覧（そのモードの形）、OUT-006の注記、警告（OUT-011。FRM-049を含み、FRM-106を除く）、別枠・待機・登録のみ（OUT-009）、書く先のない注記の「注記:」の行（OUT-007）、治療時間の目安（OUT-005。グループがある総力モードだけ。グループがある通常モードではグループの見出し（OUT-019）に含める）、同盟の移動人数（OUT-019。グループがある通常モードだけ）、同盟メンバー表（OUT-014。総力モードで出すかはQ-108による）を入れる。同盟移動のファイルには、同盟移動（OUT-016）、グループの登録（OUT-017）、入出の人数と総力（OUT-018。FRM-106の警告を含む）を入れる。出力するたびに、`output/`の中に実行の時刻のフォルダ（`output/<実行の時刻>/`）を新しく作って、これらのファイルと編成のJSON（DAT-010）を書き、前の回の出力を上書きしない（旧Q-147、利用者の決定、2026-11-10）。フォルダ名は実行した計算機の現地時刻の`YYYYMMDD-HHMMSS`（Windowsで使えない`:`を含めない）とし、同じ名前のフォルダがあれば`-2`、`-3`を付ける。出力しない実行（終了コード2の入力のエラーと解がない場合、3の番号付きの質問（FRM-075）、4の時間切れ）では作らない。CLIは2つ目の位置引数で`output/`のような出力のフォルダを受け取り、`.md`で終わるパス（以前の版の出力のパス）は、置き方が変わったことを示して入力のエラーとする（旧Q-151、旧Q-152）。現行の実装（ADR 0036）は隊のファイルを`チーム編成.md`、編成のJSONを`チーム編成.json`として書く |
| DAT-010 | 運用操作 | 編成のJSONは、出力した編成を次の実行へ前回の編成として渡すためのファイルとし、出力するたびに隊のファイルと同じ`output/<実行の時刻>/`へ書く。運用者は共有した回のファイルを、書き換えずに`--previous`で渡す（旧Q-147、利用者の決定、2026-11-10）。キーは`schema_version`（この版は1。違う版は読み込みエラー）、`created_at`（実行の時刻。フォルダ名と同じ時刻で、編成を始めた時刻。時差付きのISO 8601、DAT-002）、`teams`（隊の一覧）、`supports`（応援の一覧）、`waiting`（待機）、`undecided`（別枠）とする。隊の1件は`team`（隊の番号）、`leader`（DAT-007の`{"name": 参加者一覧の名前, "alliance": 参加者一覧の同盟}`の形）、`start`（出撃開始時刻（FRM-041）。戦闘開始から出撃する隊は`null`）、`members`（所属メンバーの一覧。参加時間が確定したリーダーを含む）を持つ。応援の1件はDAT-009の`support`と同じく`member`、`time`、`team`とする。待機と別枠の1件は`member`を持つ。総力モードの移動先（FRM-071、旧Q-122）は、隊と、待機・別枠の各1件の任意の`destination_alliance`とする。総力モードを加える分割案の7で書き、それまでは書かないが読み書きできる（旧Q-154）。前回からの移動の数（FRM-071、FRM-037の⑦）は分割案の5で比べる。それまでは読み込みと今回の参加者一覧との照合だけに使い、編成に使わないことと、今回の参加者一覧に名前と同盟の組で当たらない人数（同盟が変わった人を含む）を、名前を書かずに示す。当たらない人がいてもエラーにしない（旧Q-153）。人数を示す実行は作成者の仮定A-42の(6)による。未知のキー、型の誤り、成り立たない記録は、名前を書かずに位置とキーを示して読み込みエラーにする。細部は作成者の仮定A-42による。このファイルは個人名を含むため、Git管理外のイベントのフォルダに置く（DAT-001） |

のように、すべての隊をちょうど1回ずつ番号の一覧で書け、番号は続かなくてよい。同じグループにしたい組（FRM-077）は
`"together_pairs": [[{"name": "カイ", "alliance": "AAA"}, {"name": "レン", "alliance": "BBB"}]]`、待機と参加時間未定の既定の移動先（FRM-112）は
`"default_destination_alliance": "BBB"`の形で書く。上の例は総力モードのため、これらを含めない（作成者の仮定A-31）。

`answers.json`（上の例とは別の、戦闘開始が21:00で10隊の回の例。第7隊の21:00の問いに、第10隊を22:00から出撃させ、第10隊に所属するカイが21:00と21:30に第7隊を応援すると答えた。形を示す例である。応援は休止の判定に数えず、休止中の隊は応援先にならないため、この回答が受け入れられるのは、第10隊を遅らせたことで第10隊に入れなくなった序盤の参加者を、第7隊の所属にして21:00と21:30に出撃させられる場合に限る。上の4隊の例では、応援先になる第5隊以降がないため応援を書けない）

```json
{
  "answers": [
    {
      "target": {"team": 7, "time": "21:00"},
      "late_start": {
        "team": 10,
        "start": "22:00",
        "support": [
          {"member": {"name": "カイ", "alliance": "AAA"}, "time": "21:00", "team": 7},
          {"member": {"name": "カイ", "alliance": "AAA"}, "time": "21:30", "team": 7}
        ]
      }
    }
  ]
}
```

`チーム編成.json`（編成のJSON、DAT-010。上の4隊の例とは別の、戦闘開始が21:00で10隊の回の`output/20260101-205230/`のファイル。第1〜6隊、第8隊、第9隊と、隊のメンバーの大部分を省いた。第10隊は22:00から出撃し、カイが21:00と21:30に第7隊を応援した。総力モードの移動先`destination_alliance`は、通常モードでは書かない）
